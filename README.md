# Mati-Ni

포워더 정산시스템. 매출·매입을 기록하고, 관세대납 흐름을 추적하고, B/L별·월별·거래처별
손익을 조회하는 단순한 프로그램.

## 실행
```bash
npm install
npx prisma generate
npx prisma db push
npm run dev   # http://127.0.0.1:3000
```
또는 `run-matini.bat` 더블클릭 (서버 실행 + 브라우저 자동 오픈).

처음 실행하면 로그인 계정이 하나도 없으므로 `/login`에서 "관리자 계정 만들기" 화면이 뜬다
— 이메일/비밀번호를 입력해 첫 관리자 계정을 만들면 그 뒤부터는 일반 로그인 화면이 뜬다.

PDF 인보이스 자동입력 기능을 쓰려면 `.env`에 `ANTHROPIC_API_KEY`를 설정해야 한다
(https://console.anthropic.com 에서 발급). 키가 없으면 그 기능만 동작하지 않고, 나머지
화면은 정상 작동한다.

## 핵심 규칙
- **매출은 B/L 번호 단위로 1건씩 등록**한다(`/vouchers`). 손익 집계는 전부 이 매출의
  "작성일자" 기준이며, 매입일자·관세대납일자는 집계 기준에 쓰지 않는다.
- **매입은 총액 단위로 등록**하고(`/vouchers`), 그 총액이 어느 B/L에 얼마씩 들어갔는지
  사람이 직접 배분한다 — 균등분배·비율계산 없음. 배분 합계는 항상 매입 총액과 일치해야
  등록된다(불일치 시 등록 거부).
- **매출과 매입 중 어느 쪽을 먼저 등록해도 된다.** 배분은 B/L번호로 저장되고, 그 번호의
  매출이 아직 없으면 "매출 미등록" 상태로 남아있다가 나중에 그 번호로 매출이 등록되는
  순간 자동으로 연결된다.
- **관세대납(`/customs`)은 손익에 포함되지 않는 별도의 자금흐름**이다. 특정 B/L을 대신해
  낸 대납액과, 그걸 나눠서 회수한 내역(부분회수 가능)을 따로 추적한다. 미회수잔액 =
  대납액 - 회수합계. 매입과 마찬가지로 **매출보다 먼저 등록해도 된다** — B/L번호로 저장해
  두고, 나중에 그 번호로 매출이 등록되면 자동으로 연결된다.
- **거래처(`/parties`)는 매출처(고객)/매입처(공급자) 구분 없이 하나의 마스터**로 관리한다.
- **B/L 손익 = 매출액 - 그 B/L에 배분된 매입액**. 관세대납은 위 계산에 안 들어간다.
- **로그인이 필요하다.** 이메일/비밀번호 계정이 없으면 어떤 화면에도 못 들어간다
  (`/login` 제외). 계정마다 "세금계산서 탭 열람 권한"과 "관리자 권한"을 따로 설정할 수
  있다 — 아래 "로그인과 권한" 참고.

## 데이터 모델
- `User` — 로그인 계정 (이메일·비밀번호 해시·관리자 여부·세금계산서 열람 권한)
- `Party` — 거래처(통합). 코드(순번)·사업자등록번호(항상 `000-00-00000`)·담당자명·담당자
  연락처·담당자 이메일. 사업자등록번호와 담당자 이메일은 세금계산서 자동등록/열람권한에
  쓰인다 — 아래 "세금계산서 조회" 참고
- `PartyContactEditHistory` — 거래처 담당자 정보(담당자명·연락처·이메일) 수정 이력. 수정 전/후
  값과 사유를 남기고, 최초 입력은 "초기설정"으로 기록한다
- `Sale` — 매출 1건 = B/L 1건 (날짜·거래처·금액)
- `Purchase` — 매입 1건 (날짜·거래처·총액)
- `PurchaseAllocation` — 매입 총액을 B/L별로 배분한 금액 (수기입력)
- `CustomsAdvance` / `CustomsRecovery` — 관세대납·회수 (별도 자금흐름)
- `TaxInvoiceAttachment` — 세금계산서 승인번호별로 첨부한 인보이스 파일명·확정된 B/L·승인 시각
  (`approvedAt`)
- `TaxInvoiceEditHistory` — 승인된 세금계산서의 B/L·첨부파일 수정 이력(수정 전/후 값·사유·처리자)
- `TaxInvoiceRecord` — 엑셀 업로드로 읽은 세금계산서 원본(승인번호가 식별자) — 이후
  "조회" 시 바로빌 API 결과와 자동으로 합쳐진다
- `TaxInvoiceSeq` — 세금계산서 내부 관리번호(매출 `I00001`, 매입 `O00001`). 승인번호별로
  방향별 순번을 붙여두고, 한 번 부여된 번호는 바뀌지 않는다

매출을 삭제하면 그 B/L에 걸린 매입배분·관세대납(및 회수내역)도 함께 삭제된다. 매입 총액
자체와 거래처는 그대로 남고 배분만 없어진다.

## 화면
- `/dashboard` — 이번달/누적 손익, 관세대납 미회수 총액, 최근 6개월 매출-배분매입 추이,
  거래처별 손익 Top5, 최근 매출. 새 집계 규칙은 없고 아래 화면들의 계산을 그대로 모아 보여줌.
- `/vouchers`("일반전표") — 더존 스타일 한 줄 빠른입력으로 관세 외 매출·매입을 등록하고, 구분
  컬럼 하나로 합친 단일 목록에서 확인/수정. 목록에는 세금계산서코드·거래처코드·거래처명·B/L이
  각각 별도 열로 나오고, **B/L이 여러 건인 매입은 B/L별로 한 줄씩** 펼쳐진다. 자세한 내용은
  아래 "전표 빠른입력" 참고.
- `/customs`("관세전표") — 관세대납 한 줄 빠른입력 + **한 건 = 한 줄 목록**(`CustomsTable`).
  매입 세금계산서를 "관세전표"로 등록하면(아래 참고) 여기 함께 나타난다. 아래 "관세전표 목록"
  참고.
- `/pnl` — 손익조회: 월별 / B/L별 / 거래처별 탭
- `/bank`("입출금내역") — 바로빌 계좌조회 API로 등록된 계좌의 입출금내역을 기간별 조회
  (조회 전용). 아래 "입출금내역 조회" 참고.
- `/parties` — 거래처 등록/목록 (매출·매입에서 쓰이는 거래처는 삭제 불가). 코드·사업자등록
  번호·담당자명·담당자 연락처·담당자 이메일 컬럼이 있다 — 아래 "거래처 담당자 정보와 수정
  이력", "거래처 자동등록", "세금계산서 열람 범위" 참고.
- `/tax-invoices` — 바로빌 홈택스 매입매출조회 API로 국세청 전송완료된 세금계산서를 월별
  조회 (조회 전용, 매출/매입 등록과는 무관). 계정별로 열람 권한이 있어야 보인다. 관리자가
  아니면 담당 거래처(아래 참고)의 세금계산서만 보인다.
- `/users` — 로그인 계정 관리 (관리자 전용): 계정 등록/초대, 관리자/일반 권한, 세금계산서
  열람 허용 여부, 비밀번호 재설정, 삭제. 초대 기능은 아래 "사용자 초대" 참고.
- `/login` — 로그인 화면. 계정이 하나도 없으면 최초 관리자 계정 생성 화면이 대신 뜬다.

### 탭을 떠났다 돌아와도 조회조건이 유지된다
다른 탭에 갔다가 사이드바로 돌아오면 **그 탭에서 마지막으로 보던 조회조건이 그대로 복원된다**
(예: 세금계산서에서 7월·매입으로 조회 → 일반전표 → 다시 세금계산서 = 7월·매입 그대로).
두 조각으로 구현했다:

1. **조회조건을 URL 쿼리에 담는다.** 세금계산서는 `?direction=purchase&month=2026-07`처럼
   구분·조회년월·과세유형·기준일자를 URL에 반영하고(`TaxInvoiceSearchForm`), 손익조회는
   원래부터 `?view=bl` 식으로 URL을 쓴다. 덕분에 새로고침·뒤로가기·주소 공유에서도 같은
   조건이 유지된다.
   - 세금계산서는 **URL을 초기값으로만 읽고 그 뒤로는 상태 → URL 한 방향으로만 쓴다.**
     URL을 계속 되읽어 상태에 반영하면 `router.replace` ↔ 상태 갱신이 서로를 트리거해 무한
     루프가 된다. 기본값(과세유형=과세+영세, 기준일자=작성일자)은 URL에서 생략해 주소를
     짧게 유지한다.
2. **사이드바가 탭별로 "마지막으로 보던 전체 URL"을 기억한다**(`Sidebar.tsx`,
   `sessionStorage`의 `matiNi:lastUrl:{탭경로}`). 사이드바 링크의 `href`를 그 주소로 바꿔두기
   때문에, 탭을 다시 누르면 조건이 붙은 주소로 돌아간다. `sessionStorage`를 쓰는 이유는
   브라우저 탭을 닫으면 지워져서 다음에 새로 열 때 몇 주 전 조회조건이 남아있지 않게 하려는
   것이다.
   - `sessionStorage`는 서버에 없으므로 **렌더 중이 아니라 `useEffect`에서 읽는다**(렌더 중에
     읽으면 하이드레이션 불일치가 난다).

이 구조라서 **앞으로 어느 탭에 필터를 추가하든 그 상태를 URL 쿼리에 담기만 하면 자동으로
유지된다** — 사이드바 쪽은 더 손댈 필요가 없다. 필터가 없는 탭(일반전표·관세전표·거래처·
대시보드·사용자관리)은 기억할 조건이 없어 지금도 그냥 동작한다.

`useSearchParams()`를 쓰지만 `(app)` 레이아웃이 쿠키를 읽어(`getCurrentUserFresh`) 이 하위
라우트 전체가 동적 렌더링이라, 정적 프리렌더에서 요구되는 Suspense 경계 문제는 발생하지
않는다(`next build`에서 모든 `(app)` 라우트가 `ƒ`로 표시되는 것으로 확인).

## 목록 열 정렬 (오름차순/내림차순)
**모든 목록 화면의 데이터 열은 헤더를 눌러 정렬할 수 있다.** 규칙을 화면마다 따로 구현하면
"빈 값이 어디로 가는지", "세 번 누르면 어떻게 되는지"가 표마다 달라져서, 공용 헬퍼
(`src/lib/tableSort.ts`)와 공용 헤더 컴포넌트(`src/components/SortableTh.tsx`)로 한 군데 모았다.

- **클릭 1회 = 오름차순 → 2회 = 내림차순 → 3회 = 정렬 해제(원래 순서)**. 해제를 넣은 이유는
  표마다 기본 순서에 의미가 있어서다(전표는 최근 날짜부터, 손익 거래처별은 이익 큰 순 등) —
  해제가 없으면 기본 순서로 돌아가려고 새로고침해야 한다.
- **빈 값(`null`/`""`/`"-"`)은 정렬 방향과 무관하게 항상 뒤로 보낸다.** 내림차순으로 뒤집을 때
  빈 행이 맨 위로 올라와 실제 데이터를 가리는 게 가장 불편해서다.
- 숫자는 숫자로, 문자는 `localeCompare(ko, { numeric: true })`로 비교한다 — B/L 번호·거래처
  코드처럼 숫자가 섞인 문자열에서 `"10" < "9"`가 되는 사전식 비교를 피한다.
- **화면에 보이는 글자로 정렬한다.** 예: 구분은 `sale/purchase`가 아니라 "매출"/"매입"으로,
  권한은 `admin/user`가 아니라 "관리자"/"일반"으로 비교한다(값과 화면 순서가 어긋나지 않게).
- 정렬 중인 열은 헤더 글자색이 진해지고 `↑`/`↓`가 붙는다. 키보드(Enter/Space)로도 누를 수 있고
  `aria-sort`를 내보낸다.
- **버튼·입력만 있는 열은 정렬 대상이 아니다** — 관리(수정/삭제), 세금계산서 "보기", 등록/첨부,
  회수 입력, 초대 링크, 비밀번호 재설정, 묶음 선택 체크박스.
- **여러 줄이 한 논리행인 표는 묶음 단위로 정렬한다**(`sortGroupedRowsBy`) — 일반전표는 한 전표가
  B/L별로 여러 줄이므로 줄 단위로 정렬하면 같은 전표의 줄들이 흩어져 왼쪽 연결선이 무의미해진다.
  정렬 값은 그 전표의 첫 줄에서 뽑으므로, B/L·금액으로 정렬하면 "첫 배분 기준"이 된다.
  관세전표의 회수 세부 줄은 대표 줄 바로 아래에 렌더되므로 대표 줄만 정렬하면 따라온다.
- 정렬은 **화면에서만 다시 늘어놓는 것**이다 — 서버를 다시 부르지 않고, 바로빌도 다시 호출하지
  않는다. 합계(tfoot)는 정렬과 무관하게 전체 행을 더한 값이다.
- 그래서 `/pnl`·`/parties`·`/users`·대시보드의 표는 **클라이언트 컴포넌트로 뽑았다**
  (`PnlTables`·`PartyTable`·`UserTables`·`RecentSalesTable`) — 페이지가 서버 컴포넌트라
  `useState`를 쓸 수 없었기 때문이다. 집계·조회는 계속 서버에서 하고 정렬만 클라이언트에서 한다.
  Date는 클라이언트로 넘기지 않고 서버에서 문자열로 포맷해 보낸다.
- 대시보드 "최근 6개월 추이" 표도 정렬되지만, **기본 순서는 위 차트와 같은 월 순서**다 —
  금액순으로 정렬하면 표와 차트 순서가 달라지므로 3번째 클릭으로 원래 순서로 되돌릴 수 있다.

## 수정 이력의 수정자
`PartyContactEditHistory`·`TaxInvoiceEditHistory`·`SaleBlEditHistory` 모두 `changedByEmail`에
**수정한 계정의 로그인 아이디(=이메일)** 를 남기고, 팝업 이력 목록에 `{시각} · 수정자 {아이디} ·
{사유}` 형태로 보여준다. 예전에는 이메일을 `·`로만 이어붙여서 가운데 값이 무엇인지 알기
어려웠기 때문에 **"수정자" 라벨을 붙였다.**

## 비밀번호를 잊었을 때 (복구)
관리자 비밀번호를 잊으면 앱으로는 들어갈 방법이 없다(`/users`의 "비밀번호 재설정"은 이미 관리자로
로그인해야 쓸 수 있다). 그때는 **이 컴퓨터에서 CLI로** 재설정한다:

    npm run reset-password -- --list                     # 계정 목록 확인
    npm run reset-password -- sol@techtaka.com "새비밀번호"

- **웹 화면으로 만들지 않은 이유**: 로그인 없이 열리는 비밀번호 재설정 화면을 두면 앱에 접근할
  수 있는 누구나 관리자 계정을 가져갈 수 있다. 이 앱은 메일 발송 기능이 없어서 "본인 확인 메일"
  같은 절차를 만들 수도 없다. CLI는 이미 서버 파일과 `dev.db`를 직접 만질 수 있는 사람만 쓸 수
  있으므로 **새로운 공격 경로가 생기지 않는다.**
- 이메일은 대소문자를 가리지 않는다(앱의 `login()`과 같게 소문자로 정규화). 비밀번호는 8자
  이상이어야 하고, 앱과 똑같이 bcrypt로 해시해서 저장한다.
- **계정이 하나도 없으면** `/login`이 "최초 관리자 계정 생성" 화면으로 바뀌므로 거기서 새로
  만들면 된다(`createFirstAdmin`). 그래서 마지막 관리자 계정은 앱에서 삭제할 수 없게 막아뒀다.
- 비밀번호를 바꿔도 **기존 로그인 세션은 유지된다** — 세션 쿠키는 비밀번호와 별개다. 다른 곳의
  세션까지 끊어야 하면 그 브라우저에서 로그아웃하면 된다.

## 로그인과 권한
- 세션은 DB 세션 테이블 없이 **서명된 쿠키(stateless)** 로 처리한다(`src/lib/sessionToken.ts`,
  `src/lib/session.ts`). `.env`의 `SESSION_SECRET`로 HMAC 서명하며, 유출되면 세션을 위조할
  수 있으니 git에 올리지 않는다. 쿠키는 7일 유효.
- 라우트 보호는 두 단계다: `src/proxy.ts`(Next 16의 `middleware` 후속 기능)가 로그인 여부만
  빠르게 확인해 `/login`으로 리다이렉트하고, `(app)/layout.tsx`와 각 Server Action이 DB에서
  다시 확인한다(관리자가 권한을 바꾼 게 재로그인 없이 바로 반영되어야 하므로).
- 계정 권한은 두 가지뿐이다: `role`(admin/user)과 `canViewTaxInvoices`(세금계산서 탭 열람).
  전부 `/users`(관리자 전용)에서 관리한다. 마지막 관리자 계정은 강등·삭제할 수 없다.
- 비밀번호는 `bcryptjs`(순수 JS)로 해시한다 — Windows에서 `better-sqlite3` 때 겪었던 네이티브
  빌드 문제를 피하려고 네이티브 바인딩이 있는 `bcrypt` 대신 이걸 썼다.
- "비밀번호 찾기" 같은 이메일 발송 기능은 없다 — 비밀번호를 잊으면 관리자가 `/users`에서
  직접 재설정해줘야 한다.

### 사용자 초대
`/users`(관리자 전용)에서 이메일·권한·세금계산서 열람 허용 여부를 정해 "초대 링크 생성"을
누르면 `UserInvite` 행이 만들어지고, `/invite/{token}` 링크가 화면에 뜬다(복사 버튼 제공).

- **이메일이 자동으로 발송되지는 않는다** — SMTP/이메일 API 연동이 없어서, 관리자가 이 링크를
  직접(메신저·메일 등으로) 전달해야 한다.
- 초대받은 사람이 그 링크를 열면(`src/app/invite/[token]/page.tsx`, 로그인 없이 접근 가능 —
  `src/proxy.ts`의 matcher에서 `invite` 제외) 자기 비밀번호만 정해서 가입을 완료한다. 이메일과
  권한(`role`/`canViewTaxInvoices`)은 초대 시점에 관리자가 정한 값 그대로 적용되고 바꿀 수
  없다. 가입 즉시 자동 로그인되어 `/dashboard`로 이동한다.
- 초대 링크는 7일 후 만료되고, 가입이 완료되거나 관리자가 목록에서 "취소"하면 사라진다. 같은
  이메일로 다시 초대하면 기존 초대(토큰)를 덮어쓴다.
- 초대 링크의 기준 주소는 `.env`의 `APP_URL`(기본값 `http://127.0.0.1:3000`)이다 — **지금은
  로컬(127.0.0.1)에서만 접속되므로, 초대받은 사람이 다른 컴퓨터에서 링크를 열려면 서버를
  네트워크에서 접근 가능하게 배포하고 `APP_URL`을 그 주소로 바꿔야 한다.** 그 전까지는 초대
  링크도 이 컴퓨터에서만 열린다.

## 전표 빠른입력 (더존 스타일)
매출·매입은 `/vouchers`("일반전표") 맨 위의 한 줄짜리 폼(`VoucherQuickEntry`)으로, 관세대납은
`/customs`("관세전표")의 별도 한 줄짜리 폼(`CustomsQuickEntry`)으로 등록한다. 둘 다 값을 채운
뒤 Enter(또는 "등록" 버튼)를 누르면 그 자리에서 바로 등록되고 칸이 비워져 다음 건을 이어서
입력할 수 있다(날짜/거래처는 유지, B/L·금액·비고만 비움).

- `/vouchers`의 "구분"은 매출/매입만 고를 수 있다(관세는 없음) — **매입은 항상 B/L 1개 =
  전액 배분으로 단순화**한다. 한 인보이스를 여러 B/L로 쪼개야 하면 세금계산서 화면의
  "묶어서 등록"/멀티 B/L 팝업을 쓰거나, 아래 "다건명세서 업로드"를 쓴다.
- `/customs`의 빠른입력은 거래처 칸이 없다(관세대납 모델 자체에 거래처 개념이 없음) — B/L·
  대납일·대납액·비고만 입력한다.
- **`/vouchers` 목록의 열은 `날짜 · 구분 · 세금계산서코드 · 거래처코드 · 거래처명 · B/L ·
  금액 · 비고 · 관리`다.** 거래처는 다른 화면과 달리 `[코드] 이름` 한 칸이 아니라 **코드와 이름을
  별도 열로 분리**했다(`formatPartyLabel`을 쓰지 않는다) — 코드로 정렬·훑기 좋게 하기 위함이다.
  - **"세금계산서코드"는 그 전표가 어느 세금계산서에서 등록됐는지**를 내부 관리번호
    (매출 `I00001` / 매입 `O00001`)로 보여준다. 세금계산서 화면 밖이라 번호를 **읽기만** 한다
    (`getTaxInvoiceNumbersByKeys`) — 번호 부여는 세금계산서를 조회하는 시점에만 일어나야 하므로
    여기서 `assignTaxInvoiceNumbers`를 부르지 않는다. 직접 입력한 전표는 `-`다.
  - **B/L이 여러 건으로 배분된 매입은 배분 1건 = 1행으로 펼친다.** 예전엔
    `PRKS26060051 외 3건` 한 줄로 접어서 보여줬는데, 그러면 어느 B/L에 얼마씩 들어갔는지 이
    화면에서 알 수 없었다. **금액도 전표 총액이 아니라 그 B/L에 배분된 금액**이라, 같은
    세금계산서코드의 줄들을 더하면 전표 총액이 된다(예: `O00048` 5줄 합계 = 6,129,097).
    - **같은 전표의 줄들은 B/L 칸 왼쪽 세로선으로 묶어서 표시한다.** 처음엔 두 번째 줄부터 `↳`를
      붙였는데, 그러면 첫 줄이 부모이고 나머지가 그 **하위 항목**처럼 읽힌다 — 실제로는 N개 배분이
      서로 대등하다. 그래서 첫 줄까지 포함해 모든 줄에 같은 세로선·같은 들여쓰기를 준다.
      - 묶음 안쪽 줄들 사이에는 **가로 구분선을 넣지 않는다**(마지막 줄에만 넣는다) — 줄마다 선이
        그어지면 세로선이 토막토막 끊겨 각 줄이 별개 전표처럼 보인다.
      - 묶음이 아닌 줄에도 같은 두께의 **투명** 테두리와 같은 들여쓰기를 줘서 B/L 글자의 x좌표를
        맞춘다(안 그러면 2px+8px씩 어긋나 보인다).
    - **수정·삭제 버튼은 펼쳐진 첫 줄에만 둔다** — 줄마다 삭제 버튼이 있으면 그 B/L만 지워지는
      것처럼 보이는데, 실제로는 전표 전체(모든 배분)가 지워진다. 확인 문구에도 `N건 배분이 전부
      함께 삭제됩니다`라고 밝힌다.
    - 정렬은 날짜 내림차순이지만, 같은 전표에서 펼쳐진 줄들은 반드시 붙어 있어야 하므로 날짜가
      같으면 전표 id → 배분 순서로 이어서 정렬한다.
- **`/vouchers` 목록에서 바로 수정할 수 있다** — 행의
  "수정"을 누르면 그 자리에서 편집 폼으로 바뀌고, "저장"을 누르면 반영된다. **세금계산서
  화면에서 등록된 건(`Sale.ntsSendKey`/`Purchase.ntsSendKey`가 있는 건)과, B/L이 여러 건으로
  배분된 매입은 "잠김" 표시만 뜨고 여기서 수정할 수 없다** — 세금계산서에서 등록된 값은
  세금계산서 화면에서만 바뀌어야 하고(다시 첨부해서 재등록), 배분이 여러 건인 매입은 이 단순
  폼으로 안전하게 편집할 수 없기 때문이다. 삭제는 두 경우 모두 가능하다.
- 관세대납은 `/vouchers` 목록에는 안 나타난다(모델 자체에 거래처가 없어 매출/매입과 구조가
  다름) — `/customs`에서 확인한다.

### 지원하는 매입 인보이스 양식 (API 없이 오프라인 인식)
첨부한 PDF는 **정형 양식 파서를 순서대로** 시도한다. 각 파서는 자기 양식이 아니면 빈 배열을
돌려주므로 그냥 이어 붙이면 되고, 셋 다 실패할 때만(그리고 `ANTHROPIC_API_KEY`가 있을 때만)
AI 추출로 넘어간다 — **정형 양식은 전부 API 없이 읽는다.**

| 파서 | 양식 | 식별 표지 | 화물 식별자 |
|---|---|---|---|
| `parsePurchaseStatement` | 지출결의서 리스트 (여러 건) | 끝이 `YYYY-MM-DD`인 줄 반복 | House/Master No |
| `parseArgoInvoice` | 해상 단건 INVOICE | `Total Amount` + `B/L No` | `H B/L No` / `M B/L No` |
| `parseAirInvoice` | **항공(AWB) 단건 INVOICE** | `Total Amount` + `HAWB No`/`MAWB No` | `HAWB No` / `MAWB No` |

**항공 양식을 왜 따로 만들었나**: 같은 회사가 발행하는 같은 제목("INVOICE") 문서인데 표기와
배치가 다르다. 해상 파서는 가드가 `B/L No` 문구를 요구해서 `HAWB No`만 있는 항공 문서를 즉시
거부했고(실제로 O00010이 이 때문에 "미인식"으로 남았다), 값을 찾는 방식도 다르다:

    해상: 라벨 줄 "H B/L No"        → 값이 몇 줄 뒤에 따로 나온다
    항공: "HAWB No DSC084969"       → 라벨과 값이 **한 필드**에 붙어 있다

- 금액은 합계행에서 읽는다: `"0 | 3,063,059 | 2,009.09 | T o t a l"` → `field[0]`=VAT,
  `field[1]`=원화 합계. 글자 사이에 공백을 넣어 찍는 양식이라(`T o t a l`) 공백을 지운 뒤
  비교하고, `S u b T o t a l`은 제외한다. 합계행을 못 읽으면 `"Total Amount KRW 3,063,059"`
  한 필드에서 뽑는 예비 경로를 쓴다.
- 거래처는 `"[C005] 주식회사 이너시아 | : | Customer"`에서 읽고 앞의 내부 코드 `[C005]`는 떼어낸다
  (거래처 마스터의 이름과 맞춰야 하므로).
- **가드를 좁게 유지한다** — `Total Amount`와 `HAWB No`/`MAWB No`가 **둘 다** 없으면 빈 배열을
  돌려준다. 억지로 읽어 잘못된 금액을 만드는 것보다 "미인식"이 안전하다. 실측으로 지출결의서·
  PaymentList 양식을 이 파서에 넣어도 0줄임을 확인했다.
- 파일명의 `_미인식_`은 **첨부한 시점**에 붙는 이름이다. 파서를 개선한 뒤에도 이름은 그대로
  남으므로, 예전에 미인식으로 올린 파일은 **다시 첨부하면** 정상 인식된다.

### 지출결의서 명세서의 VAT 열 — 공급가액을 정확히 읽는 핵심
포워더 "지출결의서 리스트"(ARGO 양식)의 **B/L별 합계는 부가세를 포함한 금액**이다. 그래서 그
숫자를 그대로 쓰면 세금계산서 공급가액과 딱 그 부가세만큼 어긋난다. 이 양식에는 **`W/F / VAT`
열에 B/L별 부가세**가 인쇄되어 있으므로, 그걸 읽어 빼면 **안분 없이 공급가액과 정확히 맞는다**:

| B/L | 문서 합계 | VAT | 공급가액 |
|---|---|---|---|
| PRKS26060051 | 1,640,251 | 0 | 1,640,251 |
| PRKS26060063 | 357,964 | 815 | 357,149 |
| PRKS26060063 | 1,538,155 | 0 | 1,538,155 |
| PRKS26070016 | 631,543 | 1,410 | 630,133 |
| PRKS26070026 | 1,969,579 | 6,170 | 1,963,409 |
| **합계** | **6,137,492** | **8,395** | **6,129,097** ← 세금계산서 공급가액 |

- **필드 위치**: `pdf-parse`가 뽑는 필드 순서는 **화면에 보이는 것의 역순**이다. 화물 한 건은 3줄이고,
  그중 원화 비용줄(필드 12개)에서 `field[0]`이 그 줄의 Total, **`field[1]`이 VAT**다. 필드 수가 12가
  아니면 다른 양식이거나 줄이 밀린 것이므로 **VAT를 0으로 두고 넘어간다** — 틀린 값을 빼서 금액을
  망치는 것보다 안전하다.
- 파서는 `amount`(문서에 인쇄된 합계), `vat`(= W/F 열 금액), `supplyAmount = amount - vat`를 함께
  돌려주고(`ParsedStatementLine`), 화면은 **`supplyAmount`를 B/L 배분 금액으로 채운다**.
- **빼낸 W/F 금액은 버리지 않고 "W/F" 줄로 되살려 넣는다**(`unissuedFromLines`). B/L 줄에서만
  빼면 그 금액이 전표에서 사라져 **전표 총액이 지출결의서와 맞지 않기** 때문이다. 결과는
  이렇게 된다 — 세금계산서 2건을 묶은 경우의 실측:

      B/L별 배분 (= 세금계산서 공급가액)
        PRKS26060051   1,640,251
        PRKS26060063     357,149
        PRKS26060063   1,538,155
        PRKS26070016     630,133
        PRKS26070026   1,963,409   소계 6,129,097
      + W/F 줄                        8,395
      ─────────────────────────────────────
        전표 총액                  6,137,492  = 지출결의서 리스트 합계

  즉 **세금계산서 2건 + W/F 1건 = 구성요소 3개**가 한 전표에 들어간다. B/L은 비워둔다 — 특정
  B/L에 속하는 금액이 아니라 문서 전체에 붙은 항목이고, 비워두면 B/L별 손익에 섞이지 않는다.
- 명칭 목록 맨 앞이 **`W/F`** 이고(그 다음 `부가세 / 영세율 / 면세 / 해외운임 / 기타`), 추출 시
  자동으로 `W/F`가 선택된 채 금액이 채워진다. 다른 성격의 금액이면 명칭만 바꾸면 된다.
- **화면에 그 사실을 밝힌다**: "오프라인 파싱으로 B/L 5건을 인식해 아래에 채웠습니다
  (문서의 W/F 8,395원은 B/L 금액에서 빼고 "W/F" 줄로 따로 넣었습니다)". 화면 금액이 문서에 인쇄된
  B/L 합계와 다른 이유가 이것이기 때문이다.
- ARGO 단건 INVOICE 양식(`argoInvoiceParser`)에는 VAT 열이 따로 없어 `vat: 0`으로 둔다. AI 추출도
  VAT를 못 채우므로 `vat`/`supplyAmount`는 **선택 필드**이고, 없으면 `amount`를 그대로 쓴다.

### 인보이스 금액은 안분하지 않는다 — 차액은 "미발행" 줄로
**예전에는 인보이스에서 읽은 B/L별 금액을 세금계산서 공급가액에 맞춰 비율로 눌러 담았다(임의
안분).** 그러면 B/L마다 실제 청구액이 조금씩 왜곡되어(예: 1,640,251 → 1,638,007) 인보이스와
대조가 안 됐다. 지금은 **인보이스 금액이 그대로 들어가고**(`buildRawBlRows`), 세금계산서와 맞지
않는 차액은 **명칭을 붙인 별도 배분 줄**로 넣는다.

- **배분 합계는 공급가액 합계와 합계금액(공급가액+세액) 합계 둘 다 정답으로 받는다**
  (`allocationTargets`). 입력 경로가 두 가지여서다:
  - PDF를 첨부하지 않으면 B/L 줄이 세금계산서 **공급가액** 기준으로 채워진다.
  - 인보이스를 첨부하면 인보이스 금액이 그대로 들어가는데 거기엔 **부가세가 섞여 있다**
    (실제 예: B/L별 합 6,137,492 = 공급가액 6,129,097 + 세액 8,395).
  한쪽만 정답으로 두면 다른 경로에서 늘 세액만큼 차액이 남아 매번 "부가세" 줄을 입력해야 한다 —
  **부가세는 관심 대상이 아니고, 진짜로 세금계산서에 없는 금액만 잡아내는 것이 목적이다.**
- **미발행 줄**: 명칭을 `부가세 / 영세율 / 면세 / 해외운임 / 기타(직접입력)` 중에서 고르고, 금액과
  (선택) B/L을 적는다. "남은 차액 N 채우기" 버튼이 두 기준 중 **가까운 쪽까지의 차액**을 제안하지만
  **자동으로 채우지는 않는다** — 자동으로 넣으면 그것도 결국 임의 처리라서, 사람이 확인하고 넣는다.
- **B/L을 비워두면** 특정 B/L에 속하지 않는 줄이 된다. `PurchaseAllocation.saleId`는 `blNo`와 같은
  B/L의 매출이 있을 때만 채워지므로, 빈 `blNo`는 **어떤 매출과도 매칭되지 않아 B/L별 손익에 섞이지
  않는다**(부가세를 특정 B/L 손익에 넣지 않으려면 비워둔다).
- **전표로 그대로 전달된다**: `PurchaseAllocation.label`(스키마 추가)에 명칭이 저장되고, 일반전표
  목록의 B/L 칸에 배지로 함께 보인다. 줄마다 명칭이 필요해서 `Purchase.note`가 아니라 배분 줄에
  뒀다(한 전표에 세금계산서분과 미발행분이 섞인다).
- **매출 묶음에는 적용하지 않는다** — 매출은 인보이스에서 금액을 읽지 않고 세금계산서 공급가액을
  그대로 쓰므로 예전 규칙(공급가액 일치)이 맞다.

### 관세전표는 "청구 내역"이다 — 현금 이동이 아니다
**세금계산서에서 온 관세 내용은 관세사·포워더가 우리에게 청구한 금액**이고, 실제 입금·출금은
은행 거래이므로 **입출금내역 화면에서 가져온다.** 그래서 열 이름을 "출금정보(대납)"에서
**"청구정보(관세)"** 로, "입금정보(회수)"에서 **"회수정보"** 로 바로잡았다(빠른입력의 `대납일`·
`대납액`도 `청구일`·`청구액`으로). 예전 이름은 이 화면이 현금 출납인 것처럼 읽혀서, 같은 돈이
입출금내역에도 있는데 두 번 나간 것처럼 오해할 수 있었다.

- "회수정보"의 값은 여전히 **수기 기록**(`CustomsRecovery`)이다 — 실제 은행 입금과 자동으로
  대조되지는 않는다. 그 연결은 아직 없다(아래 "앞으로" 참고).
- `CustomsAdvance.paidDate`/`amount`라는 필드 이름은 그대로 두었다 — 이름을 바꾸면 기존 데이터
  마이그레이션이 필요한데, 뜻은 주석으로 밝혀두는 것으로 충분하다.

### 관세전표 목록 — 입금 / 청구 / 출금 세 묶음
열은 **묶음 단위**로 읽는다. 각 묶음의 첫 열에 왼쪽 세로선(`GROUP`)을 줘서 어디까지가 한 묶음인지
눈에 보이게 했다 — 날짜·금액 열이 6개나 붙어 있으면 어느 날짜가 어느 금액의 짝인지 헷갈린다.

    B/L · 거래처코드 · 거래처명 ‖ 입금일 · 입금액 ‖ 청구일 · 청구액 ‖ 출금일 · 출금액 ‖ 비고 · 삭제

- **청구**(가운데)만 이 화면이 직접 들고 있는 값이다. **입금·출금은 입출금내역에서 찾아 붙인다.**
- **매칭 조건: 금액이 청구액과 같고 + 거래처가 같은** 은행 거래. 거래처는 입출금내역의 거래처
  매칭 규칙(`matchPartyForMatch` 정규화 + 사람이 지정한 별칭)을 **그대로 재사용**한다 — 같은
  판단을 두 곳에서 따로 구현하면 어긋난다. 실측: 은행 `주)이너시아 / 3,063,059 입금`이 관세전표
  `주식회사 이너시아 / 청구액 3,063,059`에 붙었다.
  - **거래처를 모르는 은행 거래는 금액만으로 붙이지 않는다** — 오답 위험이 크다.
  - 같은 금액·같은 거래처 거래가 여러 건이면 **가장 이른 것**을 쓴다. 규칙 없이 고르면 조회할
    때마다 화면이 달라진다.
- **`등록`·`회수`·`미회수`·`회수 입력` 열은 없앴다.** 실제 입금을 입출금내역에서 가져오게 된
  이상, 같은 돈을 수기로 또 기록하는 "회수"는 두 개의 진실을 만든다. `미회수`도 그 수기 값에
  기대던 계산이었다.
  - `CustomsRecovery` 테이블과 `addRecovery`/`deleteRecovery` 액션은 **남겨뒀다** — 지울 이유는
    없고 되살릴 여지도 있다. 화면에서만 빠졌다(제거 시점에 기록 0건이라 숨겨지는 데이터도 없었다).
  - `등록`(어느 세금계산서에서 왔는지)은 `CustomsAdvance.ntsSendKey`에 그대로 저장된다 — 화면에서
    빼도 **중복 등록 가드는 계속 그 값을 쓴다.**

### 세금계산서 ↔ 전표 매칭은 승인번호가 먼저다 (B/L은 전표를 특정하지 못한다)
목록의 "등록됨"·"전표종류"·"외 N건"은 모두 이 매칭에서 나온다(`src/lib/taxInvoiceAttachments.ts`).

- **1순위: 승인번호(`ntsSendKey`)** — Sale / Purchase / CustomsAdvance를 그 값으로 찾는다.
  세금계산서가 정확히 어느 전표가 됐는지 가리키는 유일한 키다.
- **2순위: 첨부의 B/L — 단, 확정된 건에만.** 묶음 구성원은 대표 1건만 승인번호를 가져서 B/L로
  찾아야 하는데, 등록하면 반드시 확정 시각이 남으므로(묶음은 구성원 전원에게 남는다) 확정이
  없다는 건 아직 어느 전표도 되지 않았다는 뜻이다.

왜 B/L로는 안 되나 — **같은 B/L에 전표가 둘 이상 걸린다.** `DSC084969`에는 관세대납
3,063,059(O00010)과 항공운임 매입 배분 29,439,549이 함께 있다. B/L로 찾으면 먼저 조회된
매입이 답이 되어, 관세전표로 등록한 O00010이 "일반전표 · 외 10건"으로 보였다. 확정 조건이
없을 때는 반대 방향의 오탐도 났다 — 등록조차 안 된 O00017이 B/L만 겹치는 남의 전표에 붙었다.

부수적으로 `blCount`("외 N건")에서 **빈 B/L을 세지 않는다** — 세금계산서 미발행분(W/F 등)은
특정 B/L에 속하지 않아 blNo가 빈 문자열이고, 그걸 세면 실제 B/L 수보다 하나 많게 나온다.

### 세금계산서 목록에 "전표종류" 열이 있다 (일반전표 / 관세전표)
매입 세금계산서는 **일반전표(매입)로도, 관세전표로도** 등록될 수 있어서 "등록됨"만으로는 어느
화면에 가서 봐야 하는지 알 수 없다. 품목이 `DUTY`인데 일반전표로 등록된 건이 실제로 있다 —
품목만 보고는 짐작할 수 없다는 뜻이다.

- 값은 `AttachmentStatus.matchedKind`에서 온다(이미 있던 값이다). 라벨은 **화면 이름**을 쓴다 —
  예전 표기("매입등록"/"관세등록")는 동작을 말해서 어디로 가야 하는지가 드러나지 않았다.
  매출은 Sale이라 항상 `일반전표`다.
- 예전에는 이 값이 "등록/첨부" 칸 안의 작은 글씨였다. 그 칸에는 B/L 버튼·첨부 버튼·오류 문구가
  같이 들어가 훑어볼 수가 없어서 **독립 열로 뺐고, 원래 자리의 인라인 표기는 지웠다**(두 곳에
  같은 값이 있으면 하나만 고쳐질 때 서로 어긋난다).
- 다른 열과 같이 정렬된다(`voucherKind`) — 관세전표로 등록된 건만 모아 보려면 이 열을 누른다.
- 묶음은 세금계산서 여러 건이 전표 1건으로 등록되므로 종류도 하나다 — 대표행에만 값이 있다.

### 일반전표에도 실제 입출금을 붙인다 (매출=입금 / 매입=출금)
`날짜 · 구분 · 세금계산서코드 · 거래처코드 · 거래처명 · B/L · 금액 ‖ 입출금일 · 입출금액 ‖ 비고 · 관리`

- **매출은 은행 입금, 매입은 은행 출금**을 찾는다. 한 전표가 둘 다 가질 일은 없으므로(구분이
  이미 매출/매입을 말해준다) 열은 `입출금일`·`입출금액` 한 쌍만 두고, 금액 색으로 구분한다
  (입금=초록, 출금=빨강).
- **금액은 전표 총액 기준이다 — B/L 배분액이 아니다.** 은행에서 돈이 움직인 단위는 전표 총액이라,
  배분액으로 찾으면 5건으로 쪼갠 매입은 영원히 안 붙는다.
- 여러 B/L로 펼쳐진 매입은 **첫 줄에만** 입출금을 보여준다 — 줄마다 같은 입출금이 반복되면 그
  금액이 여러 번 움직인 것처럼 읽힌다.
- 매칭 규칙은 관세전표와 **공용**이다(`src/lib/bankMatch.ts` — `createBankMatcher`). 금액이 같고
  거래처가 같은 거래, 여러 건이면 가장 이른 것, 거래처를 모르는 거래는 금액만으로 붙이지 않는다.
  같은 판단을 두 곳에서 따로 구현하면 한쪽만 고쳐져 화면끼리 답이 달라진다.
- **전표 금액은 공급가액, 은행 금액은 합계금액이다** — 단위가 다르다. 그래서 공급가액만으로
  찾으면 세액이 0인 영세율 건(해외운임)만 붙고 과세 건은 전부 놓친다. 세금계산서의 **실제
  세액**을 더한 금액으로도 찾고(10%를 곱하는 추정이 아니다 — 영세율·면세가 섞이면 추정이
  틀린다), 그렇게 붙은 건은 화면에 `VAT 포함`으로 밝힌다. 세액은 `TaxInvoiceRecord`에서
  승인번호로 찾으므로 **한 번이라도 조회한 세금계산서만** 쓸 수 있다(은행거래 사본과 같은 이유).
  묶음 매입은 전표에 대표 1건의 승인번호만 남아서, 나머지는 같은 대표 B/L을 가진 첨부로
  되찾아 세액을 합산한다 — 묶음의 일부만 사본이 있으면 반쪽 합계로 틀린 금액을 붙이게 되므로
  아예 모른다고 본다.
- **입금까지 확인된 매출 행은 초록 음영**(`bg-pos/10`) — 입출금내역의 "확정"과 같은 색이다.
  매입(출금 확인)은 칠하지 않는다: "돈이 나갔다"를 같은 초록으로 칠하면 매출의 입금 확인과
  같은 신호로 읽힌다.
- 실측: 65줄 중 10줄이 붙었다(공급가액 그대로 6 + VAT 포함 4)(예: `그란데클립에프앤비코리아 / 전표 10,680,659 → 은행 입금
  2026-08-10 10,680,659`). 나머지는 아직 그 기간을 입출금내역에서 조회하지 않았거나 금액이
  일치하는 은행 거래가 없는 경우다.

### 입출금내역을 로컬에 보관한다 (`BankTransaction`)
입출금내역은 조회할 때마다 바로빌에서 새로 받아오는 값이라 DB에 없었다. 그래서 다른 화면에서
"이 청구에 해당하는 실제 입금/출금이 있나?"를 물어볼 방법이 없었고, 화면을 열 때마다 바로빌을
부르면 계좌·기간마다 수 초씩 걸려 쓸 수 없다.

그래서 **입출금내역 화면에서 조회할 때마다 그 결과를 `BankTransaction`에 upsert**하고(키:
`TransRefKey` — 같은 기간을 여러 번 조회해도 중복되지 않는다), 다른 화면은 이 표만 읽는다.

- **한 번이라도 조회한 기간만 매칭에 쓸 수 있다.** 조회하지 않은 기간은 관세전표의 입금/출금이
  비어 보이고, 그 칸에 마우스를 올리면 "해당 기간을 입출금내역에서 아직 조회하지 않았을 수도
  있습니다"라고 알려준다.
- 별도의 동기화 화면이나 배치는 만들지 않았다 — 쓰는 사람이 입출금내역을 보는 것이 곧 동기화다.


- **"등록" 열**은 이 관세대납이 **어느 세금계산서에서 등록됐는지**를 내부 관리번호(`O00010` 등)로
  보여준다. 관세전표 화면에서 직접 입력한 건은 `직접입력`으로 구분한다 — 세금계산서 대조 대상인지
  아닌지가 여기서 갈린다.
- 이걸 만들려면 `CustomsAdvance.ntsSendKey`가 필요해서 컬럼을 추가했다(선택, 옛 데이터는 null).
  **이 컬럼이 없어서 생겼던 구멍도 함께 막았다** — 예전에는 `findDuplicateVoucherMessage`가
  Purchase/Sale만 확인해서 **관세전표로 등록한 건은 중복 등록 가드가 적용되지 않았다.** 지금은
  관세전표도 확인한다.
- 번호는 **읽기만** 한다(`getTaxInvoiceNumbersByKeys`) — 번호 부여는 세금계산서를 조회하는
  시점에만 일어나야 하므로 이 화면에서 새 번호가 매겨지지 않는다.
- 합계줄과 "↳ 회수" 펼침 줄도 같은 묶음 구분을 따른다. 열을 하나 늘리면 이 두 군데도 같이
  고쳐야 열이 어긋나지 않는다(지금은 헤더·본문·합계 모두 11칸. 회수 열을 없애면서 "↳ 회수"
  펼침 줄도 사라졌다 — 펼치기 버튼이 그 열에 있었으므로 도달할 수 없는 코드가 됐다). 열을 하나 늘리면 이 두
  군데도 같이 고쳐야 열이 어긋나지 않는다.

### 관세전표의 거래처
`CustomsAdvance`에 **거래처(`partyId`, 선택)** 가 있다. 예전에는 관세대납에 거래처를 아예 두지
않고 B/L로 연결된 매출의 거래처를 빌려 보여줬는데, 그러면 **매출이 아직 없는 대납은 상대를
적어둘 방법이 없었다.**

- **거래처 마스터에 이미 있는 거래처만 지정할 수 있다.** `PartySearchSelect`
  (`src/components/PartySearchSelect.tsx`)로 **코드 또는 거래처명을 타이핑해서 검색**해 고른다.
  여기서 새 거래처를 만들지 않는 이유: 전표를 입력하다 오타로 거래처가 새로 생기면 거래처 목록이
  금방 지저분해지고 손익 집계도 거래처가 쪼개져 어긋난다. 거래처 추가는 `/parties`에서만 한다.
  - `<select>`를 안 쓴 이유는 거래처가 수십~수백 건이면 스크롤로 찾기 어렵고, 코드로 찾는
    사람과 이름으로 찾는 사람이 둘 다 있어서다. 코드는 **앞자리 일치**를 위로 올려서 아는 코드를
    치면 첫 줄에 나온다. ↑↓/Enter로도 고를 수 있고, Enter가 폼 저장으로 새지 않게 막아뒀다.
  - 화면에서 검색으로만 고르게 해뒀지만 Server Action은 직접 호출될 수 있으므로
    `resolveCustomsPartyId`가 **서버에서도 존재 여부를 다시 확인**한다(없는 id면 외래키 오류로
    터지는 대신 사람이 읽을 수 있는 메시지를 돌려준다).
  - 스키마는 `onDelete: Restrict` — 관세전표가 쓰고 있는 거래처는 실수로 지워지지 않는다.
- **거래처 칸이 뜨는 곳**: 세금계산서 매입 등록에서 **"관세전표"를 골랐을 때만** 뜬다(단일 확인
  팝업·멀티 B/L 팝업·묶음 팝업 3곳 공통). 일반전표(매입)로 등록하면 세금계산서 공급자가 그대로
  거래처가 되므로 이 칸이 필요 없다. `/customs` 한 줄 빠른입력에도 있다(빠른입력에서는 대납일처럼
  **연속 입력 시 값을 유지**한다 — 같은 거래처로 여러 건 넣는 경우가 많다).
- 멀티 B/L·묶음으로 여러 `CustomsAdvance`가 생길 때는 **전부 같은 거래처**를 넣는다(세금계산서
  1건에서 나온 대납이라 상대는 하나다).
- **목록 표시 우선순위**: 전표에 지정된 거래처 → 없으면 B/L로 연결된 **매출의 거래처(`(매출)` 표시)**
  → 둘 다 없으면 `-`. `(매출)`을 따로 표시하는 이유는 그 매출이 지워지면 사라지는 값이라 직접
  지정된 거래처와 성질이 다르기 때문이다.
- 옛 데이터는 `partyId`가 `null`이라 그대로 `(매출)` 폴백으로 보인다.

### 매입 세금계산서 → 일반전표(매입) vs 관세전표
세금계산서 화면에서 매입 세금계산서를 첨부/등록할 때(단일 등록 확인 팝업, 멀티 B/L 팝업,
묶어서 등록 팝업 전부) "등록 유형" 라디오로 **일반전표(매입, `Purchase`)** 또는
**관세전표(`CustomsAdvance`)** 중 하나를 골라야 한다 — 매입 세금계산서 중 상당수가 실제로는
관세(DUTY)라서, 손익에 포함되면 안 되는 금액이 매입으로 잘못 잡히는 걸 막기 위해서다.

- **항상 사용자가 직접 고른다** — 자동으로 등록되지 않는다. 다만 품목명에 "관세"나 "DUTY"가
  있으면(`looksLikeCustoms`, `src/components/TaxInvoiceSearchForm.tsx`) 관세전표를 기본값으로
  미리 골라둔다(그래도 바꿀 수 있다).
- 멀티 B/L(한 인보이스가 여러 B/L을 커버) 상태에서 관세전표를 고르면, `Purchase` 하나로 묶는
  대신 **B/L마다 별도의 `CustomsAdvance`**를 만든다 — 관세대납은 애초에 여러 건을 하나로
  묶는 개념이 없기 때문이다.
- 첨부 칸의 매칭 상태(`AttachmentStatus.matchedKind`)도 이제 세 가지다: 매출 연결됨(`sale`),
  매입 연결됨(`purchase`), 관세전표 등록됨(`customs`) — 어느 쪽으로 등록됐는지 그대로 보여준다
  (`src/lib/taxInvoiceAttachments.ts`가 `PurchaseAllocation`과 `CustomsAdvance`를 둘 다
  확인한다).

### 관세전표 목록 — 한 건이 한 줄, 출금정보/입금정보
관세대납은 한 건이 "**출금(대납) 1회 + 입금(회수) N회**"로 이뤄진다. 예전에는 건마다 카드를
만들고 그 안에 회수 표를 따로 그려서 건수가 늘면 세로로 계속 길어졌는데, 지금은 **한 건 =
한 줄**인 표로 보여준다(`CustomsTable`, `src/components/CustomsTable.tsx`):

`B/L · 거래처 · 출금정보(대납) · 입금정보(회수) · 미회수 · 비고 · 회수 입력 · 삭제`

- **출금정보** = 우리가 대신 낸 관세 → `대납일 + 대납액`.
- **입금정보** = 고객에게서 돌려받은 회수 → `최근 회수일 + 회수 합계 + "N건 펼치기"`.
  회수가 여러 번이어도 한 줄을 유지하려고 합계만 보여주고, **"N건 펼치기"를 누르면 그 줄 아래로
  세부 회수 내역이 열린다**(개별 회수 삭제는 거기서 한다) — 목록을 한 줄로 유지하면서도 세부
  관리 기능을 잃지 않게. 회수가 없으면 `-`.
- **회수 입력도 같은 줄에 인라인으로** 둔다(날짜·금액·비고·등록) — 건마다 별도 폼 영역을
  만들지 않는다.
- 맨 아래 합계행에 대납·회수·미회수 총액이 나온다. 미회수가 남아있으면 빨간색, 다 회수되면
  초록색.
- 한 건이 여러 `<tr>`(대표 줄 + 펼친 회수 줄들)을 내므로 **`<Fragment key>`로 감싼다** — 그냥
  `<>`로 감싸면 React key 경고가 난다.

## 인보이스 PDF 업로드 (자동입력)
`/vouchers`의 "PDF 자동입력" 업로더(구분에 따라 매출/매입용으로 바뀐다)와 `/customs`의
관세대납용 "PDF 자동입력" 업로더에 PDF를 올리면 Claude(Anthropic API, `claude-opus-5`)가
PDF를 직접 읽어 그 줄의 칸을 채워준다 — 등록 전에는 항상 사람이 값을 확인/수정할 수 있고,
자동으로 저장되지 않는다.

- 매출: B/L번호·날짜·거래처명·금액·비고
- 매입(단일 인보이스): 날짜·거래처명·금액·비고 (B/L 배분은 자동화 대상이 아니라 항상 수기)
- 관세대납: B/L번호·대납일·금액·비고

추출된 B/L번호는 이미 등록된 매출과 번호가 일치할 때만 자동 선택되고, 일치하는 게
없으면 경고 문구만 뜨고 사용자가 직접 선택해야 한다. 인보이스 양식은 거래처마다 달라서
값을 못 찾으면 해당 필드는 비워둔다.

**거래처명은 매출/매입 업로드 시 자동 등록된다.** 추출된 거래처명이 기존 거래처와
(부분일치 기준으로) 매칭되면 그 거래처를 그대로 쓰고, 매칭되는 게 없으면 그 이름으로
새 거래처를 즉시 등록해서 선택해준다 — 더존 업로드에서 신규 거래처코드를 자동등록하던
것과 같은 패턴. 폼 위에 "거래처 OOO를 자동 등록했습니다" 문구로 표시된다. (관세대납은
문서 자체에 거래처명이 없어서 대상이 아니며, B/L이 매칭된 경우에만 그 매출의 거래처를
그대로 보여준다.)

### 매입 — 다건 명세서 업로드 (House No/Master No 기준)
포워더 원가정산서처럼 **한 PDF 안에 여러 화물(House No/Master No)의 청구액이 나열된
명세서**는(예: 홀마트 지출결의서 리스트) 전표 빠른입력에서 구분을 "매입"으로 두면 나타나는
작은 "다건명세서 업로드" 버튼(`PurchaseStatementQuickUpload`)으로 처리한다. 파일을 올리면
미리보기 팝업이 뜨고, 문서의 각 줄(House No 우선, 없으면 Master No)과 그 줄의 청구총액을
모두 추출한 뒤:

- 각 줄의 번호를 기존 매출(Sale.blNo)과 **정확히 일치**하는 것만 자동 매칭한다.
- 등록되는 매입 총액(Purchase.amount)은 문서의 전체 합계가 아니라 **매칭된 줄의 합계만**이다
  — 매칭 안 되는 줄까지 포함하면 "배분 합계=매입 총액" 규칙이 깨지기 때문이다.
- 매칭되지 않은 줄(아직 매출이 등록 안 된 B/L 등)은 등록에서 제외되고, 그 번호 목록이 매입의
  비고(note)에 자동으로 남는다 — 나중에 그 매출을 등록한 뒤 별도로 매입에 반영해야 한다.
- 미리보기 표에서 각 줄이 어느 매출에 매칭됐는지(또는 안 됐는지) 등록 전에 확인할 수 있다.

**추출 방식은 여러 단계다(`extractPurchaseStatementPdf`, `src/app/(app)/purchases/actions.ts`):**
1. **오프라인 파싱을 먼저 시도한다 — API 키 불필요.** 화물 한 건이 "①합계 ②원화환산 비용줄
   ③ETD/House No/거래처/날짜" 3줄 고정 패턴으로 반복되는 정형 명세서(테크타카 로지스틱스
   지출결의서 리스트 등)라면 `pdf-parse`로 텍스트만 뽑아 규칙 기반으로 100% 정확히 읽는다
   (`parsePurchaseStatement`, `src/lib/purchaseStatementParser.ts`) — AI 호출이 아예 없다.
2. 그 패턴이 하나도 안 맞으면, ARGO/테크타카 로지스틱스의 **B/L 1건짜리 단건 INVOICE
   양식**(예: 관세(DUTY) 대납 인보이스)인지 오프라인으로 한 번 더 시도한다
   (`parseArgoInvoice`, `src/lib/argoInvoiceParser.ts`). 이 양식은 HTML 표를 PDF로 찍어내는
   방식이라 라벨(H B/L No 등)이 전부 먼저 한 덩어리로 나오고 값은 뒤에 다른 순서로 나오는데,
   "라벨 뒤에 이어지는 라벨 전용 줄들을 건너뛰고 그다음 처음 나오는 순수 영숫자 코드를 값으로
   본다"는 위치 기반 휴리스틱으로 H B/L No(없으면 M B/L No)와 "Total Amount ... KRW ..."
   금액을 찾는다. 항목이 1건짜리 인보이스라 결과도 0건 또는 1건만 나온다 — 못 찾으면(다른
   레이아웃 변형 등) 조용히 빈 배열을 반환하고 다음 단계로 넘어간다.
   - **새로운 정형 양식이 더 생기면 이 목록에 파서를 하나씩 추가하면 된다** — 각 파서는
     서로의 표지 문구(예: "Total Amount"/"B/L No")로 자기 양식이 아니면 바로 빈 배열을
     반환하도록 짜여 있어 오탐(다른 양식을 잘못 인식) 위험 없이 나란히 시도할 수 있다.
3. 위 오프라인 파서가 전부 실패한 다른 양식의 PDF라면, `ANTHROPIC_API_KEY`가 설정돼 있을
   때만 Claude로 추출을 한 번 더 시도한다. 키가 없고 오프라인 파싱도 실패하면 값을 직접
   입력해야 한다.

미리보기/첨부 화면에는 어느 방식으로 인식됐는지("오프라인 파싱" / "AI로 추출됨")가 표시된다
(둘 중 어느 오프라인 파서가 맞혔는지는 구분해서 보여주지 않는다 — 사용자 입장에서는 둘 다
"오프라인 파싱"일 뿐이다).

**`serverExternalPackages`에 `pdf-parse`/`pdfjs-dist`가 반드시 있어야 한다**
(`next.config.ts`). 이게 없으면 Next.js가 이 패키지를 서버 번들에 같이 묶어버리는데,
`pdfjs-dist`는 워커 스크립트를 실행 시점에 파일 경로로 직접 찾기 때문에 번들 안에서는 그
경로가 사라져 "Setting up fake worker failed"로 항상 실패한다(`parsePurchaseStatement`도
`parseArgoInvoice`도 둘 다 내부적으로 `pdf-parse`를 쓰므로 똑같이 영향받는다) —
`extractPurchaseStatementPdf` 호출부의 `catch`가 이 예외를 삼켜서 겉으로는 "정해진 명세서
양식을 인식하지 못했습니다"로
보이는 바람에, 실제로는 오프라인 파싱이 원래 인식했어야 할 PDF까지도 전부 인식 실패로
잘못 나온다(다건 명세서 업로드·묶어서 등록 팝업의 인보이스 첨부 양쪽 다 영향받는다). 이
패키지들을 제거하거나 업그레이드할 때는 이 설정이 계속 남아있는지 확인할 것.

## 업로드 원본 PDF 저장
매출/매입(단일·다건)/관세대납 어디서 업로드하든, 값 추출에 성공하면 원본 PDF가 프로젝트
루트의 `uploads/` 폴더(`.gitignore`에 포함, git에는 안 올라감)에 아래 순서로 자동 저장된다:

```
{원본파일명}_{거래처명}_{Group No}_{금액}_{Period}.pdf
```

- Group No/Period는 다건 명세서에만 있는 값이라, 없는 업로드(매출·단일 매입·관세대납)는 그
  자리를 건너뛰고 `{원본파일명}_{거래처명}_{금액}_{날짜}.pdf` 형태가 된다.
- 관세대납은 문서 자체에 거래처명이 없어서, 추출된 B/L이 기존 매출과 매칭됐을 때만 그
  매출의 거래처명을 사용한다(매칭 안 되면 거래처명 없이 저장).
- 파일명에 못 쓰는 문자(`\ / : * ? " < > |`)는 제거되고, 같은 이름이 이미 있으면 `(1)`,
  `(2)`처럼 번호가 붙어 덮어쓰지 않는다.
- 폼 등록 여부와 무관하게 **PDF를 업로드해서 값 추출에 성공한 시점에 바로 저장**된다 —
  업로드는 했는데 등록을 안 눌러도 원본은 `uploads/`에 남는다.

## 세금계산서 조회 (바로빌 홈택스 매입매출조회 API)
`/tax-invoices`에서 바로빌(Barobill)의 홈택스 매입매출조회 API로 국세청에 전송완료된
세금계산서를 월 단위로 조회한다(`GetMonthlyTaxInvoiceSalesListEx` /
`GetMonthlyTaxInvoicePurchaseListEx`, SOAP). **매출/매입(Sale/Purchase) 등록에는 자동으로
반영하지 않는다** — 지금까지처럼 전표는 수기 등록이나 PDF 업로드, 또는 아래 "행별 인보이스
첨부"로만 쌓인다. 다만 **거래처 마스터는 자동으로 반영된다** — 아래 "거래처 자동등록" 참고.

사전 준비:
- 바로빌 사이트에서 해당 사업자에 대해 **홈택스 세금계산서 연동 서비스가 이미 신청**되어
  있어야 한다(`RegistTaxInvoiceScrapEx` — 이 앱이 대신 신청해주지 않는다). 신청하면 매일
  새벽 전날까지의 세금계산서를 바로빌이 수집해두고, 이 조회 API로 언제든 꺼내볼 수 있다.
- `.env`에 `BAROBILL_CERTKEY`(연동인증키), `BAROBILL_CORPNUM`(사업자번호, 하이픈 제외),
  `BAROBILL_USERID`(바로빌 로그인 아이디)를 설정해야 한다. **홈택스 아이디/비밀번호는 이
  앱에 저장하지 않는다** — 홈택스 연동 신청 자체는 바로빌 사이트에서 이미 끝난 상태를
  전제로 하기 때문에, 이 앱이 필요로 하는 건 바로빌 자체의 인증 정보뿐이다.
- `BAROBILL_ENV`를 `"production"`으로 설정하면 운영 서버(`ws.baroservice.com`)를,
  비워두거나 `"test"`로 두면 테스트 서버(`testws.baroservice.com`)를 사용한다.
- 위 환경변수가 비어 있으면 이 탭에서 조회 시 오류 메시지만 뜨고, 나머지 화면은 정상
  동작한다.

구현은 `src/lib/barobill.ts`에서 `soap` 패키지로 바로빌 WSDL(`TI.asmx?wsdl`)을 직접
호출한다. 한 달 결과가 페이지당 100건씩 나뉘어 오므로 최대 20페이지(2,000건)까지
자동으로 이어붙여 보여주고, 그보다 많으면 화면에 "최초 2,000건까지만" 경고를 띄운다.

**`NTSSendKey`는 API 응답에서 대시 없이 24자리로 온다 — 반드시 대시를 붙여 정규화해야
한다** (`formatNtsSendKey`, `YYYYMMDD-XXXXXXXX-XXXXXXXX`). 홈택스 엑셀 업로드
(`parseHometaxTaxInvoiceExcel`)와 이 앱에 저장되는 모든 값(`TaxInvoiceAttachment`,
`Sale`/`Purchase.ntsSendKey` 등)은 전부 대시 포함 형식이라, API 결과를 그대로 쓰면 같은
세금계산서가 엑셀 업로드본과 API 결과에서 서로 다른 문자열로 보여 `mergeTaxInvoiceRows`의
승인번호 중복 제거가 실패하고 목록에 같은 건이 두 번(엑셀분+API분) 나온다 — 실제로 운영
서버 인증키를 처음 등록했을 때 이 문제로 7월 조회 건수가 48건에서 96건으로 뛰는 걸 보고
발견했다. `BAROBILL_ENV`가 `"test"`이거나 조회가 계속 실패해서 항상 저장된 업로드본으로만
폴백되던 동안에는 이 형식 불일치가 드러나지 않았다.

**단, 세금계산서 원문보기 API(`GetTaxInvoicePrintURLNKAsync`)의 `NTSConfirmNum`은 반대로
대시 없는 원본 형식을 요구한다** — 대시 포함 `ntsSendKey`를 그대로 넘기면 오류코드
-21002로 실패한다. 그래서 `getTaxInvoicePrintUrl`에서만 대시를 다시 벗겨서 보낸다
(`ntsSendKey.replace(/-/g, "")`). 즉 앱 내부 저장·표시는 전부 대시 포함 형식으로
통일하고, 바로빌 API를 호출하는 두 지점(목록 조회는 넣어야, 원문보기는 빼야)만 각자
필요한 형식으로 변환한다.

**계정별 열람 권한**: `/users`에서 `canViewTaxInvoices`를 켜준 계정만 이 탭을 볼 수 있다.
권한이 없으면 탭 자체가 사이드바에서 숨겨지고, URL로 직접 들어가도 "열람 권한이 없습니다"
문구만 보인다. 관리자가 권한을 껐다 켜면 그 계정은 재로그인 없이 바로 반영된다.

**거래처 자동등록**: 조회/엑셀업로드로 세금계산서 목록이 뜰 때마다, 그 목록에 있는 공급자·
공급받는자의 사업자등록번호(bizNo) 중 거래처 마스터(`/parties`)에 없는 곳을 자동으로
등록한다(`ensurePartiesFromTaxInvoiceRows`, `src/app/(app)/parties/actions.ts`). 이름이 같은
거래처가 이미 있는데 사업자번호가 없던 경우(수기 등록 등)는 새로 만들지 않고 그 거래처에
사업자번호를 채워 넣는다. 새로 만들어지는 거래처는 순서대로 4자리 코드(0001, 0002, ...)를
받는다 — 이미 코드가 있는 거래처 중 가장 큰 값 다음 번호를 쓰며, 동시 생성 시 코드가
겹치지 않도록 한 번에 하나씩 순차 처리한다.

**거래처 코드는 어느 화면에서든 이름과 별도 항목으로 보여준다** — 예전엔 `[0001] 프로라인해운 (주)`
처럼 한 칸에 묶었는데, 코드로 훑거나 정렬하기 어렵고 이름이 긴 거래처에서는 코드가 묻혀버려서
전부 분리했다. `formatPartyLabel`은 이제 어느 화면에서도 쓰지 않는다(함수는 남겨둠).
- **표에서는 코드와 이름을 별도 열로 나눈다** — 세금계산서 목록(`… · 코드 · 공급자 · …`),
  일반전표·관세전표·대시보드 최근매출·손익조회 거래처별은 모두 `거래처코드`·`거래처명`
  두 열이다. 코드가 아직 없는 거래처(수기 등록 직후 등)는 `-`.
  - 관세전표는 거래처를 직접 들고 있지 않고 B/L로 매출에 연결돼서 붙으므로, 매출이 아직 없으면
    코드는 `-`, 이름 칸에 "매출 미등록"이 뜬다.
- **열이 없는 곳(대시보드 거래처별 손익 Top5 막대차트)은 코드를 muted 작은 글씨로 이름 앞에
  세운다** — 대괄호로 묶지 않는다.

세금계산서 목록은 거래처가 직접 연결돼 있지 않고 사업자등록번호로만 이어지므로, 조회 시
`사업자번호 → 코드` 맵을 함께 내려준다(`getPartyCodesByBizNo` → `partyCodes`). 엑셀
다운로드에도 "거래처코드" 열이 따로 나간다.

**사업자등록번호는 항상 `000-00-00000` 한 형식으로만 저장한다**(`formatBizNo`,
`src/lib/format.ts`). 들어오는 경로마다 형식이 달라서다 — 홈택스 엑셀은 하이픈이 있고
(`201-81-90365`) 바로빌 API는 없다(`2018190365`). 예전엔 받은 문자열을 그대로 저장·비교해서
두 가지 문제가 실제로 났다:
- **같은 사업자가 두 거래처로 중복 등록됐다** — 프로라인해운이 `0001`(하이픈, 엑셀에서)과
  `0037`(하이픈 없음, API에서)로 두 번 생겼다. `bizNo`가 `@unique`인데도 형식이 달라 다른
  값으로 취급된 것이다.
- **열람권한 대조가 어긋났다** — `hasCorpNumAccess`가 `party.bizNo === corpNum`으로 비교해서,
  담당자 이메일이 설정돼 있어도 형식이 다르면 조회가 막혔다.

그래서 지금은 **저장·표시는 `formatBizNo`로 통일하고, 비교·조회는 숫자만 뽑아서
(`bizNoDigits`) 형식과 무관하게 맞춘다** — `ensurePartyByBizNo`,
`ensurePartiesFromTaxInvoiceRows`, `hasCorpNumAccess`, `filterRowsByAccess`, 인보이스 파일
라우트 전부 이 규칙을 따른다. 기존 데이터(하이픈 없던 9건)도 일괄 변환했고, 중복이던 `0037`은
매출·매입 반영이 0건이라 삭제하고 실제 매입이 붙어있던 `0001`을 남겼다.

**거래처 담당자 정보와 수정 이력**: 담당자명·연락처·이메일은 목록의 **"수정" 버튼 → 팝업**에서
바꾼다(`PartyContactEditButton`, `updatePartyContact`). 관리자만 수정할 수 있다 — 담당자
이메일이 곧 세금계산서 열람권한이라, 아무나 자기 이메일을 아무 거래처에 걸 수 없어야 한다.
- **세 값이 모두 비어있던 상태에서 처음 채우는 것은 "초기설정"으로 기록하고 사유를 묻지
  않는다**(팝업에 사유 입력칸이 아예 안 뜨고, 버튼도 "초기설정 저장"으로 바뀐다) — 매번
  "초기설정"이라고 타이핑하게 만들 이유가 없다.
- **그 뒤 수정은 사유가 필수다**(사유가 비어있으면 저장 버튼이 비활성). 저장하면
  `PartyContactEditHistory`에 **수정 전 값과 수정 후 값을 양쪽 다** 남긴다 — 무엇이 어떻게
  바뀌었는지 되짚을 수 있어야 하기 때문이다.
- 팝업을 열면 그 거래처의 지난 이력이 최신순으로 함께 보인다(`getPartyContactHistory`).
  각 줄은 `{시각} · {처리자} · {사유}` 아래에 바뀐 항목만 `담당자명: (없음) → 김담당` 형태로
  보여준다(값이 없던 자리는 `(없음)`).

**세금계산서 열람 범위(거래처별)**: 관리자(`role="admin"`)는 조회한 모든 세금계산서를 볼 수
있다. 그 외 계정은 `/parties`에서 관리자가 설정한 "담당자 이메일"이 자기 로그인 이메일과
같은 거래처의 세금계산서만 보인다(`hasCorpNumAccess`/`filterRowsByAccess`,
`src/app/(app)/tax-invoices/actions.ts`) — 사업자등록번호로 거래처를 찾아 이메일을 대조하는
방식이라, 거래처에 아직 이메일이 설정되어 있지 않으면(자동등록 직후 등) 관리자에게만 보인다.
이 필터는 목록 조회뿐 아니라 첨부·등록·"보기"(세금계산서 원문) 액션에도 똑같이 적용되어, 화면에 안 보이는
거래처의 세금계산서는 액션을 직접 호출해도 처리되지 않는다. 담당자 이메일은 아무나 자기
이메일을 걸어 열람권한을 얻지 못하도록 관리자만 수정할 수 있다(`updatePartyEmail`).

**세금계산서 번호(내부 관리번호)**: 표 맨 왼쪽 "번호" 칸에 **매출은 `I00001`, 매입은 `O00001`
부터 방향별로 각각 순번**을 매긴다(I=Income/매출, O=Outcome/매입). `TaxInvoiceSeq` 테이블에
승인번호별로 저장되고, 엑셀 다운로드에도 첫 열로 함께 나간다.
- **부여 시점은 "그 세금계산서가 조회에 처음 등장한 시점"이다** — 조회할 때 아직 번호가 없는
  건에 자동으로 붙인다(`assignTaxInvoiceNumbers`, `src/lib/taxInvoiceNumbers.ts`). 한 번의
  조회 안에서는 **작성일자(같으면 승인번호) 순**으로 매겨서 오래된 것이 작은 번호를 받는다.
- **한 번 부여된 번호는 절대 바뀌지 않는다** — 관리번호가 도중에 달라지면 그 번호로 남겨둔
  다른 기록(메모·결의서 등)과 어긋나기 때문이다. 그래서 같은 월을 다시 조회해도 번호가 그대로다.
  - 이 규칙의 당연한 결과로, **오래된 월을 나중에 조회하면 그 건들이 더 큰 번호를 받는다.**
    시간순으로 깔끔하게 매기고 싶으면 오래된 월부터 순서대로 한 번씩 조회하면 된다.
- 권한 필터(`filterRowsByAccess`) **뒤에** 번호를 부여한다 — 볼 수 없는 세금계산서에까지
  번호를 소모하지 않도록.
- 묶어서 등록된 대표행은 구성원들의 번호를 모두 이어서 보여준다(예: `O00047, O00048`) —
  합산 1행이라 하나만 보이면 어느 세금계산서들이 묶였는지 알 수 없다.

**정렬**: 작성일자·공급자(공급받는자)·사업자번호·공급가액·세액·합계금액 열 제목을 누르면 그
기준으로 오름차순/내림차순 정렬된다(한 번 더 누르면 반대 방향, 열 제목 옆에 ▲/▼로 표시).
클라이언트에서만 정렬하며 서버를 다시 호출하지 않는다.

**엑셀 다운로드**: 조회 결과 위 "엑셀 다운로드" 버튼을 누르면 화면에 이미 떠 있는 목록을
그대로 CSV로 내려받는다(서버 재호출 없음, UTF-8 BOM 포함이라 엑셀에서 한글이 안 깨진다).
진짜 `.xlsx`가 필요하면 `exceljs` 같은 라이브러리 추가가 필요한데, 내부 조회용 목록이라
CSV로 충분하다고 보고 이렇게 구현했다.

**세금계산서 원문보기**: "세금계산서" 열의 "보기" 버튼은 목록에 이미 있는 국세청 승인번호로
바로빌의 `GetTaxInvoicePrintURLNK`를 호출해 원문을 볼 수 있는 URL(60초만 유효)을 받아
새 탭으로 바로 연다 — 그 페이지에서 브라우저 인쇄 기능으로 PDF 저장이 가능하다. 바로빌
API가 원본 PDF 파일을 직접 주는 게 아니라 인쇄용 웹페이지 URL만 주기 때문이다.

**홈택스 엑셀 업로드 (관리자만)**: 바로빌에 아직 수집되지 않은 기간이거나 조회량이 부족할 때를
대비해, 홈택스의 "전자(수정) 세금계산서 목록조회" 다운로드 파일(`.xls`)을 직접 올릴 수 있다
(`src/lib/taxInvoiceExcel.ts`).

- **버튼은 조회 폼 줄의 오른쪽 끝에 작게 둔다**(`ml-auto`). 예전엔 검색 폼 아래에 설명이 붙은
  큰 카드였는데, 자주 쓰는 기능이 아닌데 화면 위쪽을 계속 차지해서 버튼 하나로 줄이고 설명은
  tooltip(`title`)으로 옮겼다.
- **관리자(`role="admin"`)만 쓸 수 있다.** 업로드한 내용은 DB(`TaxInvoiceRecord`)에 남아 이후
  모든 조회 결과에 섞여 나오므로 사실상 원본 데이터를 추가하는 행위다. 화면에서 버튼을 숨기는
  것만으로는 부족해서(Server Action은 직접 호출될 수 있다) `uploadTaxInvoiceExcel` 안에서도
  `role`을 다시 확인한다 — 화면 숨김과 서버 검증 둘 다 있다.
- 파일의 5번째 줄 제목("매출/매입 전자(수정) 세금계산서 목록조회")으로 매출/매입 구분을
  자동 인식한다 — 구분을 따로 고를 필요 없다.
- 파싱 결과는 API로 조회했을 때와 완전히 같은 표·엑셀 다운로드·"보기" UI를 그대로 쓴다.
- **업로드한 내용은 `TaxInvoiceRecord` 테이블에 승인번호(ntsSendKey) 기준으로 저장된다**
  (`src/lib/taxInvoiceRecords.ts`). 그래서 한 번 올려두면, 이후 같은 구분(매출/매입)·같은
  월로 그냥 "조회"만 눌러도 바로빌 API 결과와 자동으로 합쳐져서(승인번호 중복 시 API 쪽
  우선) 계속 나온다 — 새로고침이나 재접속으로 사라지지 않고, 매번 파일을 다시 올릴 필요도
  없다. 바로빌 조회 자체가 실패해도(자격정보 미설정 등) 저장된 업로드 내역만으로는 여전히
  조회된다. 단, 매출/매입 등록(Sale/Purchase)에는 여전히 전혀 영향을 주지 않는다 — 저장되는
  건 세금계산서 원본 데이터일 뿐, 회계 장부에 반영되는 게 아니다.
- 같은 승인번호로 다시 올리면 기존 값을 덮어쓴다(중복 저장 안 됨).
- 파싱은 `xlsx`(SheetJS) 패키지로 한다. **npm 공식 레지스트리에 올라온 `xlsx`는 알려진
  프로토타입 오염·ReDoS 취약점이 패치 안 된 채로 남아있어서(SheetJS가 0.18.5 이후 버전을
  npm에 더 이상 올리지 않음), 반드시 SheetJS가 직접 배포하는 CDN 주소로 설치해야 한다**
  (`package.json`의 `"xlsx": "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"` 참고).
  `npm install xlsx`로 재설치하면 취약한 버전이 깔리니 하지 말 것.

**행별 인보이스 첨부/등록 — 매출/매입 등록의 시작점**: 표 맨 오른쪽의 **"인보이스"·"등록/첨부"·
"확정" 세 칸**으로 세금계산서 한 건마다 그 자리에서 매출(또는 매입) 등록까지 끝낼 수 있다.
**AI(Anthropic API) 연동이 전혀 필요 없다** — 세금계산서 자체에 이미 금액(공급가액)·
거래처명·작성일자·품목이 다 있으므로, 부족한 건 B/L 번호 하나뿐이기 때문이다. 두 칸의 역할이
다르다:

- **"인보이스" 칸 = 첨부된 PDF 자체를 보여주는 칸.** 아직 첨부한 게 없으면 `—`만 뜨고,
  첨부하면 **파일명이 링크로 뜨고 클릭하면 새 탭에서 그 PDF가 열린다**
  (`/api/tax-invoice-file/{승인번호}`, `src/app/api/tax-invoice-file/[ntsSendKey]/route.ts`).
  그 옆에 **검증 배지**가 붙는다(`invoiceValidation`): `검증됨`(B/L 1건 인식 + 금액이 세금
  계산서 공급가액과 일치) / `⚠ 금액 불일치` / `⚠ 미인식`(양식 인식 실패) / `B/L N건 인식`
  (여러 건 커버하는 인보이스라 1:1 금액 비교 대상이 아님). 배지에 마우스를 올리면 상세
  내용이 tooltip으로 뜬다.
  - 이 파일 라우트는 **파일명을 URL로 받지 않고 승인번호만 받아** DB에서 파일명을 찾아 쓴다 —
    사용자가 경로를 지정할 방법이 없어 경로 탐색(path traversal) 자체가 불가능하다(그래도
    최종 경로가 `uploads/` 안인지 한 번 더 확인한다). 권한은 `canViewTaxInvoices` 필수 +
    admin이 아니면 그 거래처 담당자 이메일이 자기 이메일과 같을 때만 내려주고, 상대방을 알
    수 없으면(엑셀 업로드분이 지워진 뒤 API로만 조회되는 건 등) admin에게만 허용한다.
  - 검증 배지는 **이번 세션에 첨부/재확인한 건에만** 뜬다(`pdfExtracts`는 클라이언트 상태라
    새로고침하면 비워진다). 배지가 없다고 검증 실패가 아니며, 확정을 막지도 않는다.
- **"등록/첨부" 칸 = 실제 동작 버튼이 모인 칸.** 아직 등록 안 됐으면 **"등록"**과
  **"첨부"**(한 번 첨부한 뒤엔 "다시 첨부")가 나란히 뜬다.
  - **"등록"을 누르면 B/L 번호를 입력하는 확인 팝업이 뜬다** — 표 안에 B/L 입력칸을 두지
    않는다(예전에는 표에 인라인 입력칸이 있었는데, 등록 대상 정보를 한곳에서 확인하도록
    팝업으로 옮겼다). 첨부해서 자동 인식된 B/L이 있으면 팝업에 미리 채워져 있고, 팝업의 등록
    버튼은 B/L이 비어있는 동안 비활성 상태다.
  - **인보이스 PDF 첨부는 선택 사항이다 — 등록의 전제조건이 아니다.** 파일을 올리지 않고
    B/L만 입력해서 등록해도 되고(`registerFromTaxInvoice`가 아직 없는
    `TaxInvoiceAttachment` 행을 upsert로 그 자리에서 만들어준다), 그 뒤 "확정"/"다시 첨부"
    같은 기능이 똑같이 동작한다.
  - 등록된 뒤에는 이 칸이 `{B/L} 외 N건` + `{매출연결|매입등록|관세등록}` + 다시 첨부로 바뀐다.
    연결된 전표의 거래처·날짜는 **화면에 글자로 쓰지 않고 마우스를 올리면 tooltip으로** 보여준다
    — 거래처명은 이미 왼쪽 "공급자" 열에 있고, 이 칸이 길어지면 오른쪽 "확정" 열이 화면 밖으로
    밀려서다. 확정 여부와 "수정" 버튼은 옆의 "확정" 칸에 있다(아래 참고).
  - **`{B/L} 외 N건`을 누르면 등록내역 팝업이 뜬다**(`getRegistrationDetail` →
    `RegistrationDetail`). 이게 필요한 이유: 매입 한 건은 **여러 B/L에 걸쳐 배분될 수 있는데**
    (`PurchaseAllocation`) 목록 칸에는 대표 B/L 하나만 보여서, 정작 "어느 B/L에 얼마씩
    들어갔는지"가 화면에 전혀 안 보였다. `외 N건`의 N은 **B/L 수**(대표 제외)다 — `blCount`
    (`AttachmentStatus`)로 내려주며, 매출(`Sale`은 B/L 1건=1행)과 관세대납은 항상 1이라 `외 N건`이
    붙지 않는다.
    - 팝업에는 ① 등록 유형·거래처·일자·금액·품목, ② **B/L별 배분 내역**(B/L·배분금액·매출
      연결 여부 + 2건 이상이면 합계), ③ **함께 등록된 세금계산서 목록**(관리번호·승인번호 +
      첨부 파일명 링크)이 나온다. 매출이 아직 없는 B/L은 "미연결"로 보이고, 나중에 그 B/L로
      매출이 등록되면 자동으로 "연결됨"이 된다(`PurchaseAllocation.saleId`).
    - **읽기 전용이다.** 여기서 값을 고치지 않는 이유는 수정이 사유+이력이 필요한 별도 흐름
      ("확정" 칸의 수정 버튼)이기 때문이다 — 두 곳에서 고칠 수 있으면 이력이 갈린다.
    - 묶인 세금계산서 건수는 이제 이 칸에 `외 N건`으로 붙이지 않는다(팝업 ③에서 확인) —
      B/L 버튼에 이미 `외 N건`이 있어서 나란히 두면 무엇의 N건인지 헷갈린다.
  - **확정 직전 검증 실패가 확인된 상태면 한 번 더 물어본다**(`confirmDespiteValidation`) —
    "인식된 금액이 공급가액과 다릅니다 ... 그래도 확정할까요?"에서 취소하면 확정되지 않는다.
    완전히 막지는 않는 이유는 자동 인식이 틀릴 수도 있어서다 — 최종 판단은 사람이 한다.
- 각 칸의 내용은 모두 한 줄(`whitespace-nowrap`)로 배치해 행 높이가 늘어나지 않는다.
  체크박스를 누른 행은 배경이 옅게 강조되고, 승인번호
  칸은 폭이 좁아 잘려 보일 수 있는데(마우스를 올리면 전체 값이 tooltip으로 뜬다) 의도된
  것이다 — 이 칸을 줄인 공간으로 인보이스 칸이 한 줄에 다 들어간다.

- 같은 B/L로 여러 세금계산서가 함께 등록된 경우(묶어서 등록 등)는 목록 자체에서 **대표 1행으로
  합쳐서** 보여준다 — 공급가액·세액·합계금액은 합산, 품목은 이어붙이고, 승인번호 칸엔 "N건
  묶음"만 표시한다(`buildDisplayItems`/`renderGroupRow`, `src/components/TaxInvoiceSearchForm.tsx`).
  "펼치기"를 누르면:
  - 안내 문구("↓ 이 묶음에 포함된 세금계산서 N건 — ...")가 먼저 뜨고, 그 아래로 원래의 개별
    세금계산서 행들이 옅은 배경과 "↳" 표시로 구분되어 나타난다(각자의 원문보기 포함). "접기"로
    다시 합칠 수 있다. 개별 행은 "매입등록 외 N건"처럼 같이 묶인 다른 건수도 알려준다
    (`AttachmentStatus.bundledCount`, `src/lib/taxInvoiceAttachments.ts`).
  - **묶음에 속한 개별 행은 체크박스가 없고(새 묶음에 재선택 방지) "다시 첨부"도 할 수 없다**
    ("묶음 소속"만 표시) — 대신 대표행 자체에 "다시 첨부"가 있어서, 파일 하나를 다시 올리면
    묶음에 속한 승인번호 전부의 `TaxInvoiceAttachment.fileName`이 한 번에 갱신된다
    (`reattachGroupFile` 액션). 개별로 다시 첨부하게 두면 묶음이 깨진 것처럼 보이거나, 이미
    등록된 세금계산서를 체크박스로 다시 선택해 중복 등록하는 사고로 이어질 수 있어 막았다.
  - 대표행의 **"묶음 풀기"**를 누르면(확인창 필요) 그 등록(`Purchase` 또는 `CustomsAdvance`) 전체가
    삭제되고, 묶음에 속한 세금계산서들은 첨부 파일은 유지된 채 "미등록" 상태로 돌아간다
    (`unbundleGroup` 액션) — B/L이나 배분을 잘못 묶었을 때 되돌리는 용도다. 이 B/L에 다른 B/L
    배분이 같은 `Purchase` 안에 더 있다면(인보이스 한 건이 여러 B/L을 커버하는 경우) 그것까지
    함께 지워지므로 확인창에 이 사실을 미리 알려준다.

- 첨부하면 그 세금계산서의 "비고"(remark1)란 텍스트에서 정규식으로 B/L을 1차 추출한다
  (`src/lib/blNoExtract.ts` — "B/L:MJNGB26070308", "BL/NO:PRKS26060051외 3건" 같은 홈택스
  특유의 표기를 인식). 원본 PDF는 `uploads/`에 `{원본파일명}_{B/L}_{승인번호}.pdf`로 저장된다
  (`attachTaxInvoiceFile` 액션).
- **첨부 직후(매출·매입 공통) 그 PDF 내용 자체를 오프라인 파싱으로 바로 확인한다**
  (`extractPurchaseStatementPdf`, 첨부와 같은 `handleAttachFile` 호출 안에서 실행) — 비고
  텍스트 추측만 믿고 확인도 없이 등록까지 가버리지 않게 하기 위함이다. 결과는 승인번호별로
  기억해둔다(`pdfExtracts` state):
  - **정확히 1건만 인식되면** 그 B/L로 입력칸을 덮어쓴다 — 비고 정규식 추측보다 실제 문서
    내용이 신뢰도가 높기 때문이다. 이때 **인식된 금액과 세금계산서 공급가액이 다르면 등록
    확인 팝업에 빨간 경고("⚠ 인식된 금액(...)이 세금계산서 공급가액(...)과 다릅니다")가
    뜬다**(`amountMismatchWarning`) — 다른 세금계산서용 파일을 잘못 첨부했을 가능성을
    미리 알려주는 용도다. 다만 등록 자체를 막지는 않는다 — 오인식일 수도 있어서, 최종
    판단은 항상 사용자가 팝업에서 확인 후 내리게 한다.
  - **2건 이상 인식되면**(매입만) 비고에 "외 N건" 표기가 없었더라도 그 자리에서 바로
    "여러 B/L로 나눠 배분" 팝업이 뜬다(아래 항목 참고) — 인식된 실제 내용(공급가액에 맞춰
    비율 조정된 금액)으로 채워져 있어 균등배분 추측이 아니라 문서 값 그대로 보여준다.
    매출은 `Sale`이 B/L 1개=1행이라 이렇게 나눠 배분할 수 없으므로, 2건 이상 인식되면
    자동으로 채우지 않고 등록 확인 팝업에 전부 나열만 해서 사용자가 맞는 것을 직접 고르게
    한다(여러 건으로 나눠 등록하려면 "묶어서 등록"을 이용).
  - **인식에 실패하면**(다른 양식 등) 조용히 넘어가고, 실패했다는 사실만 기억해뒀다가 아래
    확인 팝업에서 알려준다 — 등록 자체를 막지는 않는다(문서를 못 읽어도 수기 등록은 계속
    가능해야 하므로).
- 추출된(또는 비고 추측) B/L은 화면에서 바로 확인/수정할 수 있다.
- B/L을 확인한 뒤 "매출 등록"/"매입 등록" 버튼을 누르면 바로 등록되지 않고, **등록될 내용을
  보여주는 확인 팝업**이 먼저 뜬다 — 거래처·작성일자·품목·금액(공급가액)·B/L을 정리해서
  보여주고, 그 B/L로 이미 등록된 반대쪽 거래(매입 등록이면 매출, 매출 등록이면 매입)가 있는지도
  미리 조회해서 보여준다(`previewTaxInvoiceLink` 액션) — 있으면 "자동 연결됩니다: {거래처·
  날짜}", 없으면 "나중에 등록되면 자동 연결됩니다"로 안내한다. 여기서 "등록"을 눌러야 실제로
  `Sale`(매출 목록일 때) 또는 `Purchase`+`PurchaseAllocation`(매입 목록일 때)이 만들어진다
  (`registerFromTaxInvoice` 액션). 거래처는 기존 `ensurePartyByName`으로 자동 등록/재사용되고,
  매입이 매출보다 먼저 등록되는 경우의 자동연결(`createSale`의 로직)도 그대로 적용된다.
- **승인 = 확정 (매출·매입 공통, 1단계)**: 확인/승인 팝업의 **"승인"이 곧 확정**이다 — 별도
  "확정" 버튼은 없다(예전엔 매출만 등록 → 확정 2단계였는데, 같은 일을 두 번 누르게 만들 이유가
  없어 하나로 합쳤다). 승인하면:
  - `TaxInvoiceAttachment.approvedAt`이 기록되고 **그 행이 초록 음영**으로 표시된다(매출·매입
    구분 없이 `approvedAt`만 보면 되므로 화면 로직도 하나다).
  - **별도의 "확정" 열에 `확정 MM-DD`(마우스 올리면 전체 시각)와 "수정" 버튼이 뜬다.** 이 열은
    확정을 *하는* 버튼이 아니라 **확정 상태를 눈으로 확인하는 열**이다 — 승인이 곧 확정이라 누를
    것이 없다. 등록 전에는 `—`만 보인다. "수정"을 등록/첨부 칸이 아니라 여기 둔 이유는 등록/첨부
    칸에 이미 B/L·연결상태·다시 첨부·(묶음이면) 펼치기·묶음 풀기가 몰려 있어서다.
  - **확정되면 "다시 첨부"가 사라지고 인보이스 교체는 "수정"으로만 한다** — 등록/첨부 칸에
    첨부 수단이 아무것도 남지 않는다(안내 문구조차 없이 빈 칸, 단건·묶음 대표행 공통).
    확정된 건을 표에서 바로
    다시 첨부할 수 있으면 **사유도 이력도 없이 첨부파일이 갈리기** 때문이다. 수정 팝업의
    "인보이스 다시 첨부 (선택)"이 그 자리를 대신하고, 거기서는 사유가 필수이며
    `TaxInvoiceEditHistory`에 이전/새 파일명이 남는다.
    - 아직 확정되지 않은 상태 — 전표는 있는데 승인기록이 없는 경우(`markVouchersWithoutAttachment`
      참고) — 에는 "수정" 버튼 자체가 없으므로 "첨부"를 그대로 남겨둔다. 파일이 이미 있으면
      "다시 첨부", 없으면 "첨부"로 표시한다.
  - 승인은 되돌릴 수 없다(다시 "미승인"으로 내리는 기능은 없음) — 잘못 등록했으면 "묶음 풀기"로
    등록 자체를 취소한다.

**같은 세금계산서를 두 번 등록하는 것을 두 겹으로 막는다 (이중 계상 방지)**: 2026-08-19에
프로라인해운 6,129,097원 매입이 **두 번 등록되어 있는 것**을 발견했다(백업 5개 전부에는 1건뿐,
2번째는 그날 15:10 묶음 등록으로 생성). 중복분은 배분 5건과 함께 삭제했고
(`dev.db.before-dedup-*` 백업 후), 재발을 막는 가드를 넣었다.

- **원인**: 등록 여부 판단(`getAttachmentStatuses`)이 `TaxInvoiceAttachment`만 봤다. 전표는
  있는데 첨부기록이 없는 상태 — 일반전표 화면에서 직접 등록했거나, **DB를 백업에서 복구했는데
  첨부기록은 복구되지 않은 경우** — 에서는 목록에 "미등록"으로 보여 체크박스와 "등록" 버튼이
  살아나고, 같은 매입을 한 번 더 등록할 수 있었다.
- **가드 ①(표시)**: `markVouchersWithoutAttachment`(`src/lib/taxInvoiceAttachments.ts`) —
  첨부기록이 없어도 그 승인번호로 `Purchase.ntsSendKey`/`Sale.ntsSendKey`가 있으면 "이미
  등록"으로 표시한다. 체크박스와 "등록" 버튼이 사라져 재등록 자체가 시작되지 않는다. 단
  **승인 흐름을 거치지 않은 전표라 `approvedAt`이 없으므로 "확정" 칸은 `—`이고 초록 음영도
  없다** — 없는 승인 기록을 있는 것처럼 보이게 하지 않는다.
- **가드 ②(액션)**: `findDuplicateVoucherMessage`(`.../tax-invoices/actions.ts`) —
  `registerFromTaxInvoice`·`registerBundledPurchase`·`registerBundledSale` 세 곳 모두에서,
  선택된 승인번호 중 하나라도 이미 전표를 갖고 있으면 등록을 거부한다. 화면 표시만으로는
  부족하다(Server Action은 직접 호출될 수 있고, 화면이 잠깐 "미등록"으로 보이는 순간도 있다).
  다시 등록해야 하면 기존 전표를 "묶음 풀기"로 먼저 지우면 가드가 자연히 풀린다.
- **남은 한계 두 가지**(알고 쓰는 게 낫다):
  - 묶음으로 등록된 `Purchase`는 **대표 1건의 승인번호만** 들고 있다(`ntsSendKeys[0]`). 그래서
    첨부기록이 사라진 묶음의 *구성원* 승인번호를 단독으로 등록하는 경로는 여전히 막히지 않는다.
  - `CustomsAdvance`에는 `ntsSendKey` 컬럼이 없어 **관세전표로 등록한 건은 이 가드가 적용되지
    않는다**(B/L로만 연결된다).
- **수정 팝업에서도 내용을 확인할 수 있다.** B/L을 바꾸거나 인보이스를 갈아끼우는 화면인데 정작
  무엇이 등록돼 있는지 안 보이면 감으로 고치게 되므로, 팝업에 두 블록을 함께 보여준다:
  - **현재 등록 내역** — 등록 유형·거래처·일자·전표 총액과 **B/L별 배분 줄**(명칭 배지·매출 연결
    여부 포함). "외 N건" 팝업과 **같은 액션**(`getRegistrationDetail`)을 재사용한다 — 같은 정보를
    두 곳에서 따로 계산하면 어긋난다.
  - **새 파일에서 읽은 내용** — 다시 첨부한 PDF를 등록 흐름과 같은 추출기로 읽어 B/L별 금액과
    합계를 보여준다. 저장 전에 "맞는 파일인지"를 확인할 수 있고, 예전에 안분되어 등록된 값과
    인보이스 원본 값을 **나란히 대조**할 수 있다(실제 예: 읽은 값 1,640,251 / 합 6,137,492 vs
    등록된 값 1,638,007 / 합 6,129,097).
  - **현재 파일명은 링크**라 클릭하면 그 PDF가 새 탭에서 열린다.
  - 이 팝업에서 **금액 배분을 다시 짜지는 않는다** — 구성을 바꾸려면 "묶음 풀기"로 등록을 취소하고
    다시 등록해야 한다. 그 사실을 팝업 안에 문구로 밝혀둔다.
- **승인 후 수정 — 다시첨부 + 사유 필수 + 이력**(`editApprovedTaxInvoice`): "수정" 팝업에서
  **B/L을 고치고 인보이스를 다시 첨부**할 수 있고, **수정 사유가 비어 있으면 저장 버튼이
  비활성**이다. 저장하면 `TaxInvoiceEditHistory`에 이전/새 B/L·이전/새 파일명·사유·처리자
  이메일·시각이 남고, 팝업을 다시 열면 지난 이력이 최신순으로 보인다
  (`getTaxInvoiceEditHistory`). 파일을 고르지 않으면 기존 파일을 그대로 유지한다.
  - **전표 쪽 B/L도 함께 옮긴다** — 첨부의 B/L만 바꾸면 화면엔 새 B/L이 보이는데 전표
    (`Sale`/`PurchaseAllocation`/`CustomsAdvance`)는 옛 B/L에 남아 매칭이 깨진다. 그래서 B/L이
    바뀌면 전표 쪽도 같이 갱신하고, 새 B/L로 미매칭 상태였던 매입배분·관세대납이 있으면 그
    자리에서 연결해준다.
  - **묶음이면 대표행에서만 수정하고, 묶음 전체(구성원 승인번호 전부)에 함께 적용된다** —
    하나만 바꾸면 같은 B/L을 공유해야 하는 구성원끼리 값이 어긋나 묶음 표시가 깨진다.
  - 거래처·금액·작성일자·품목은 세금계산서 원본 값이라 이 화면에서 고칠 대상이 아니다 —
    사람이 실수하기 쉬운 **B/L과 첨부파일만** 수정/이력 관리 대상으로 삼는다. (참고:
    세금계산서에서 등록된 전표는 `/vouchers`에서 아예 수정할 수 없으므로 — `updateSale`의
    `ntsSendKey` 잠금 참고 — 이 "수정"이 사실상 그 건을 고칠 수 있는 유일한 통로다.)
  - **검증 실패 상태에서 승인하면 한 번 더 물어본다**(`confirmDespiteValidation`) — 첨부한
    PDF의 금액이 세금계산서 공급가액과 다르거나 양식을 인식하지 못한 경우다. 자동 인식이 틀릴
    수도 있어 완전히 막지는 않고, 취소하면 승인되지 않는다.
  - `Sale.confirmedAt`/`SaleBlEditHistory`는 이 통합 이전의 매출 전용 구조다 — 지금 화면은
    쓰지 않지만 과거 기록 보존을 위해 컬럼/테이블은 남겨뒀다.
  - **등록 확인 팝업은(매출·매입 공통) 첨부 시점에 이미 확인해둔 PDF 인식 결과를 다시
    첨부하지 않아도 자동으로 보여준다** — 인식된 B/L·금액이 그대로 보이거나(1건, 금액이
    다르면 위에서 설명한 경고도 함께), 여러 건이 나열되거나, 인식 실패 사유가 그대로
    보인다. 다른 파일로 다시 확인하고 싶으면 같은 자리에 다시 첨부하면 된다
    (`handleConfirmFileChange`). 2건 이상 인식된 경우는 자동으로 B/L을 채우지 않고 전부
    나열만 해서 사용자가 맞는 것을 직접 골라 입력하게 한다 — 매입은 취소하고 "묶어서 등록"
    또는 "여러 B/L로 나눠 배분" 팝업을, 매출은 "묶어서 등록"을 쓰면 된다. B/L 입력칸은
    직접 수정도 가능하며, 값이 바뀌면 그 즉시 자동연결 미리보기도 다시
    조회한다(`handleConfirmBlNoChange`).
- **인보이스 한 건이 여러 B/L을 커버하는 경우(매입만)**: 위에서 설명한 대로 첨부한 PDF 내용
  자체에서 B/L이 2건 이상 인식되면 바로 열리고, 그게 아니라 PDF를 못 읽었는데 비고에는
  "외 N건" 표기가 있는 경우에도 폴백으로 열린다(`extractAdditionalBlCount`). 전자는 실제
  인식된 B/L·금액(공급가액에 맞춰 비율 조정)으로, 후자는 N+1개 행(첫 행엔 정규식으로 추출한
  B/L, 나머지는 빈 칸)이 공급가액을 균등 배분한 금액으로 미리 채워진 채로 열린다 — 사용자가
  B/L 번호를 채우고(행 추가/삭제 가능) 금액을 원하는 대로 조정한 뒤 "매입 등록"(또는 "관세
  등록")을 누르면, 그 배분대로 `PurchaseAllocation` 여러 건을 가진 `Purchase` 하나가(관세전표를
  골랐으면 배분 건수만큼 `CustomsAdvance`가) 만들어진다. 배분 합계가 공급가액과 정확히
  일치해야 등록 가능(불일치 시 에러 메시지). 이 팝업에도 묶어서 등록과 동일하게 인보이스
  (지출결의서 등) PDF를 다시 첨부할 수 있다(선택) — 첨부하면 `extractPurchaseStatementPdf`로
  House/Master No별 줄을 자동 인식해 배분 행을 채우고, 공급가액에 맞춰 비율 조정한다
  (`handleMultiBlFileChange`, 묶어서 등록과 같은 로직 —
  아래 참고). 등록 유형(일반전표(매입)/관세전표)과 무관하게 문서 구조는 동일하므로 관세로
  등록할 때도 그대로 쓸 수 있다.
- 이미 등록된(B/L이 매출/매입과 일치하는) 세금계산서는 "매출/매입 연결됨 (거래처·날짜)"만
  보여준다 — **이 매칭 여부는 저장해두지 않고 화면에 보여줄 때마다 다시 확인**하므로, 나중에
  그 Sale/Purchase를 지워도 즉시 반영된다.
- `TaxInvoiceAttachment` 테이블에 승인번호별 첨부파일명과 확정된 B/L만 저장한다(세금계산서
  원본 데이터는 여기 안 들어있고 `TaxInvoiceRecord`가 따로 담당). 같은 승인번호에 다시
  첨부하면 덮어쓴다.

**여러 세금계산서를 묶어서 등록(매출·매입 둘 다)**: 같은 화물 건이 품목별로 여러 장의
세금계산서로 나뉘어 발행되는 경우가 있다 — 매입이면 지출결의서 한 건이 OCEAN FREIGHT
세금계산서와 DRAYAGE CHG 세금계산서로 나뉘는 식(예: 프로라인해운이 같은 4개 B/L을 OCEAN
FREIGHT/DRAYAGE CHG 두 장으로 끊는 경우), 매출이면 같은 거래처가 운임 세금계산서와
취급수수료 세금계산서를 같은 B/L 한 건에 대해 따로 끊는 식이다. 이런 경우를 위해 목록의
행마다(매출/매입 공통, 단 이미 등록된 행은 재선택 방지를 위해 체크박스가 없다) 체크박스가
있고, 2건 이상 체크하면 표 위에 **"선택한 N건 묶어서 등록 (공급가액 X원)"** 버튼이 나타난다 —
묶음 등록의 기준 금액이 공급가액 합계이므로, 팝업을 열기 전에 버튼에서 바로 "얼마로 묶이는지"를
확인할 수 있게 체크한 행들의 공급가액 합계를 함께 보여준다(매출·매입 공통,
`selectedSupplyTotal`). 이 값은 팝업의 "묶음 공급가액 합계"와 항상 같다.

- **매출과 매입은 등록 방식이 다르다** — `Sale`은 원래 "B/L 1건 = 1행"이라 여러 B/L로 나눠
  배분할 필요가 없으므로, 매출 묶음은 항상 B/L 1개짜리 팝업이다(등록 유형 라디오도, "+ B/L
  추가"도 없다 — 공급가액 합계 그대로 B/L 1개에 들어가는 `Sale` 하나만 만든다,
  `registerBundledSale` 액션). 매입은 기존처럼 여러 B/L로 나눠 배분할 수 있다
  (`registerBundledPurchase`, 아래 항목들 참고).

- 같은 거래처인 행끼리만 묶을 수 있다(거래처가 다르면 에러).
- 팝업에는 선택한 각 세금계산서의 품목·공급가액·합계금액이 나열되고, 그 위에 **묶음 공급가액
  합계**가 큰 글씨로 표시된다. 처음엔 B/L 1개 행만 있고, 그 금액은 묶음 공급가액 합계로,
  B/L은 첫 번째 선택한 세금계산서의 비고에서 정규식으로 추출한 값으로 미리 채워진다(둘 다
  틀리면 직접 고치면 된다). "+ B/L 추가"로 여러 B/L로 쪼개기 시작하면 그 이후 추가되는 행은
  자동 추출/균등배분을 시도하지 않고 빈 칸으로 시작한다 — 여러 인보이스가 섞여 있어 자동
  배분이 오히려 혼란을 줄 수 있기 때문이다.
- 인보이스(지출결의서 등) PDF를 하나 첨부할 수 있다(선택) — 묶은 세금계산서 전부가 보통 같은
  문서 하나에서 나오므로, 파일은 한 번만 저장하고 선택한 승인번호 전부의
  `TaxInvoiceAttachment.fileName`에 똑같이 연결한다. **첨부하면 그 PDF를 AI 없이(오프라인
  파싱 우선) 바로 분석해서, House/Master No별 줄을 인식하면 그 내용(B/L·금액)을 배분 행에
  자동으로 채워준다**(`handleBundleFileChange`, "매입 — 다건 명세서 업로드"와 같은
  `extractPurchaseStatementPdf`를 재사용) — 채워진 뒤에도 등록 전에 반드시 확인/수정해야
  한다. 이 문서 양식을 인식 못 하면(예: House/Master No + 청구일자 패턴이 없는 다른 양식)
  기존 입력은 그대로 두고 이유를 알려준다.
  - **인식된 금액은 자동으로 공급가액 합계에 맞춰 비율 조정된다.** 명세서 자체의 합계는
    보통 부가세(또는 이 묶음에 없는 다른 세금계산서분)까지 섞여 있어 묶음 등록의 등록
    기준(공급가액 합계)과 정확히 안 맞을 때가 많은데, House별로 부가세가 얼마씩 들어있는지
    문서에서 안전하게 갈라낼 방법이 없다 — 그래서 인식된 각 줄의 금액을 공급가액 합계에
    맞는 비율만큼 균등하게 줄이거나 늘리고(반올림 오차는 마지막 줄에서 흡수), "문서상 합계
    ...에 부가세 등이 섞여 있어 비율대로 줄여서 채웠습니다(근사치)"라고 알려준다. 정확한
    House별 금액을 알고 있다면 등록 전에 직접 고치면 된다.
- **모든 등록(단일/멀티 B/L/묶음, 매출·매입 전부)은 부가세를 제외한 공급가액을 기준으로
  한다** — 합계금액(부가세 포함)이 아니다. 등록되는 `Sale.amount`/`Purchase.amount`/
  `CustomsAdvance.amount`도 전부 이 공급가액 기준이다.
- 등록하면 선택한 세금계산서 전부의 `TaxInvoiceAttachment.blNo`가 같은 대표 B/L(입력한 첫
  번째 B/L)로 갱신되어, 화면에서 전부 "매출연결"/"매입등록"으로 보인다. 날짜는 선택한 것 중
  가장 이른 작성일자, 품목명은 선택한 항목명을 " + "로 이어붙여 저장한다.
- **묶음 대표행에도 초록 음영과 "확정"·"수정"이 그대로 뜬다**(매출·매입 공통) — 승인/수정 이력 기능
  (위 "승인 = 확정" 참고)이 묶음에도 똑같이 적용된다. 다만 **묶음의 수정은 항상 대표행에서만**
  한다 — "펼치기"로 펼친 개별 구성원 행에는 수정 버튼이 없다("묶음 풀기"·"다시 첨부"와 같은
  이유: 구성원 각자가 따로 B/L을 바꾸면 같은 B/L을 공유해야 하는 구성원끼리 값이 어긋나 묶음
  표시가 깨진다) — `editApprovedTaxInvoice`가 승인번호를 배열로 받아 묶음 구성원 전체의
  `TaxInvoiceAttachment`(B/L·파일명)를 한 번에 갱신하고 이력도 구성원별로 남긴다.
- **묶음 풀기는 매출/매입이 다르게 동작한다** — 매입 묶음 풀기는 `Purchase`(그 안의 여러 B/L
  배분 포함)만 지운다. 매출 묶음 풀기는 `Sale` 자체를 지우는데, 스키마상 그 매출에 걸린
  매입배분·관세대납(및 그 회수내역)도 함께 cascade 삭제된다 — 확인창에 이 사실을 다르게
  경고한다.
- **묶음 선택 체크박스는 맨 왼쪽 전용 열에 있다** — 예전엔 "작성일자" 칸 안에 체크박스를 끼워
  넣었는데 날짜를 읽을 때 눈에 걸려서 독립 열로 뺐다. 헤더에는 글자를 두지 않았고(체크박스 열
  관례), **전체선택도 두지 않았다** — 묶음은 같은 거래처끼리만 되므로 전체선택이 유용한 경우가
  거의 없다. 묶음을 "펼치기"로 펼친 구성원 행은 체크박스 대신 이 칸에 소속 표시(`↳`)가 뜬다.
- **이미 등록된(매칭된) 행은 체크박스가 사라진다**(매출·매입 공통) — 다시 체크해서 새 묶음에
  넣으면 같은 세금계산서가 두 번 등록되는 사고로 이어질 수 있어서, 첨부/미등록 상태의 행만
  선택할 수 있게 막았다.

## 입출금내역 조회 (바로빌 계좌조회 API)
`/bank`("입출금내역", 사이드바에서 세금계산서 바로 아래)에서 바로빌 계좌조회 API로 등록된
은행계좌의 입출금내역을 기간별로 조회한다. **조회 전용이다** — 매출/매입·관세 전표에는 아무
영향을 주지 않고, 전표와 자동으로 대조하지도 않는다(그건 나중에).

구현은 `src/lib/barobillBank.ts`에서 `soap` 패키지로 `BANKACCOUNT.asmx?wsdl`을 호출한다.
세금계산서와 **같은 `.env` 자격정보**(`BAROBILL_CERTKEY`/`BAROBILL_CORPNUM`/`BAROBILL_USERID`,
`BAROBILL_ENV`)를 쓰고, 오류도 같은 방식으로 온다 — 예외가 아니라 **음수 코드**로 오므로
숫자 응답을 먼저 검사한다.

시그니처는 추측하지 않고 **WSDL을 직접 내려서 확인한 것**이다(바로빌 개발자문서 페이지는
자바스크립트로 렌더링돼 도구로 읽히지 않는다):

    GetBankAccountEx(CERTKEY, CorpNum, AvailOnly:int)
    GetPeriodBankAccountLogEx(CERTKEY, CorpNum, ID, BankAccountNum,
                              StartDate, EndDate, CountPerPage:int,
                              CurrentPage:int, OrderDirection:int)
    GetBankAccountManagementURL(CERTKEY, CorpNum, ID, PWD)

**응답 XML의 요소명은 WSDL의 타입명과 다르다 — 여기서 실제로 버그가 났다.** WSDL 타입명이
`BankAccountEx`/`BankAccountLogEx`라 그 이름으로 읽었는데, 실제 응답은 이렇다:
- 계좌 목록: `GetBankAccountExResult.**BankAccount**` (요소명에 `Ex`가 없다)
- 입출금내역: `GetPeriodBankAccountLogExResult.BankAccountLogList.**BankAccountLogEx**` (여기는 있다)

두 API의 규칙이 서로 다르다. 잘못된 키로 읽으면 **예외도 오류코드도 없이 그냥 0건**이 나와서,
운영 계좌를 등록한 뒤에도 화면에 "등록된 계좌가 없습니다"만 떴다. 지금은 두 키를 모두 보도록
(`payload.BankAccount ?? payload.BankAccountEx`) 고쳐뒀다.

`BankAccountLogEx` 필드는 전부 문자열이다 — `CorpNum, BankAccountNum, Withdraw, Deposit,
Balance, TransDT, TransType, TransOffice, TransRemark, TransRefKey, MgtRemark1, MgtRemark2`.
**`TransRefKey`는 목록 응답에도 들어있다**(처음엔 Ex 타입에만 있다고 잘못 적어뒀다) — 거래 1건을
고유하게 가리키므로 표의 React key로 쓰고, 나중에 전표와 대조할 때의 식별자로도 쓸 수 있다.
**계좌 목록은 `GetBankAccountEx2`로 받는다.** `GetBankAccountEx`는 `BankName`·`BankAccountNum`만
주는데, `Ex2`는 **별칭(`Alias`)·용도(`Usage`)·수집주기(`CollectCycle`)·은행코드**까지 준다. 계좌가
2개 이상이면 번호만으로는 어느 계좌인지 알 수 없어서 별칭이 꼭 필요하다 — 실제로 `140016218275`
(포워더매출), `140016218130`(관세대납) 두 계좌가 있고, 셀렉트에 `신한은행 140016218275 (포워더매출)`
로 나온다(`accountLabel`). 응답 요소명은 Ex2가 `BankAccountEx`, Ex가 `BankAccount`로 규칙이
일관되지 않아 **알려진 키를 모두 확인한다**(예전에 이 키를 잘못 짚어 "등록된 계좌가 없습니다"만
뜨는 버그가 있었다). 날짜는 화면에서
`YYYY-MM-DD`로 받아 바로빌이 요구하는 `YYYYMMDD`로 변환해 보낸다(`searchBankLog`).
결과는 세금계산서 조회와 마찬가지로 페이지당 100건씩 최대 20페이지(2,000건)까지 이어붙이고,
그보다 많으면 화면에 경고를 띄운다.

**`RegistBankAccount`(계좌 등록 API)는 일부러 구현하지 않았다** — 계좌 비밀번호·인터넷뱅킹
자격정보를 우리가 받아 저장하면 안 되기 때문이다. 대신 `GetBankAccountManagementURL`로 받은
**바로빌 자체 관리화면 URL을 새 창으로 열어주는 "[관리자] 계좌 등록·관리" 버튼**만 둔다
(`openBankAccountManagement`). 이 버튼은 관리자에게만 보이고, 서버 액션에서도 다시
`role === "admin"`을 확인한다(홈택스 아이디/비밀번호를 이 앱에 저장하지 않는 것과 같은 원칙).

조회조건(계좌·기간)은 URL 쿼리에 담겨서, 다른 탭에 갔다 돌아오면 그대로 유지된다(사이드바의
탭별 마지막 위치 기억 — 위 "탭을 떠났다 돌아와도 조회조건이 유지된다" 참고). 엑셀(CSV)
다운로드도 된다.

**표에 보여주는 열은 `확인서 · 거래일시 · 구분 · 입금액 · 출금액 · 은행 · 송금인/적요 ·
거래처코드 · 거래처 · 비고 · 확정`이다.**
- **잔액 열은 화면에서 뺐다**(값은 계속 받아오고 **엑셀 다운로드에는 그대로 들어간다**) — 표는
  훑어보는 용도, 엑셀은 원본 기록 용도로 나눴다.
- **"은행" 열(`TransOffice`)은 거래점/경유은행이다** — 상대 회사가 아니다(예: `기업`·`우리`·`국민`·
  `강남`·`선릉중`). 처음엔 "거래처"로 뒀다가 상대 회사로 오해할 이름이라 바꿨다. 실제 상대방
  이름은 옆의 "송금인/적요"(`TransRemark`)에 온다.
- **은행 값은 괄호를 벗겨서 보여준다**(`stripParens`) — 은행이 `(기업)`·`(우리)`처럼 괄호로 싸서
  주는 값과 `여의도`·`강남`처럼 그냥 주는 값이 섞여 있어 통일했다. **송금인 이름에는 적용하지
  않는다** — `(주)앱솔브랩`의 괄호는 상호의 일부다.
- **"송금인" 전용 필드는 바로빌·은행에 없다.** `TransRemark`(적요)가 **입금이면 송금인 이름**
  (`(주)앱솔브랩`), **출금이면 거래내용**(`해외송금`)으로 온다. 그래서 열 이름을 실제 내용에 맞게
  `송금인/적요`로 두고, 입금 건은 진하게·출금 건은 흐리게 표시한다.
- 아직 안 쓰는 정보: `TransType`(`타행PC`·`BZ뱅크`·`이자` 등 거래종류)은 받아오지만 화면에 없다.
  `GetPeriodBankAccountLogEx2`/`...TransLog`를 쓰면 `TransDirection`·`Memo`·`CurrencyCode`·
  `TransRemark2`·`CmsCode`가 더 오고, `GetBankAccountEx2`는 계좌의 별칭·용도·수집주기를 준다
  (이 계좌는 `Alias/Usage = 관세대납`, `CollectCycle = MINUTE10`).

### 거래별 상태 — 확정 / 미확정 / 제외
입출금내역 한 건에 검토 상태를 표시한다. 상태는 셋이다(표시하지 않으면 **미확정**):

| 상태 | 뜻 | 행 음영 |
|---|---|---|
| **확정** | 내용을 확인했다 | 초록 (세금계산서 확정과 같은 규칙) |
| **제외** | 대조 대상이 아니다(이자·내부이체 등) | 노랑 |
| 미확정 | 아직 안 봤다 | 없음 |

**제외의 목적은 "미확정 집계에서 빼는 것"이다.** 볼 필요 없는 건이 미확정 더미에 계속 남아
있으면 "몇 개 남았는지"가 의미를 잃는다. 그래서 `미확정 = 전체 − 확정 − 제외`로 센다.
- **제외를 노란색으로 둔 이유**: 초록은 "처리 완료"로 읽히는데 제외는 처리한 게 아니라 대상이
  아니라는 뜻이라, 확정과 눈으로 구분되어야 한다. 색은 `--warn`(`#8a6d1f`) 토큰을 새로 만들어
  `--pos`/`--neg`와 **같은 낮은 채도**로 맞췄다 — 원색 노랑을 쓰면 이 팔레트에서 혼자 튀고
  초록(확정)·빨강(음수 금액)과 나란히 있을 때 시선을 과하게 끈다.
- **제외 사유는 선택**이다(비워도 된다). 이자·내부이체처럼 자명한 건에 매번 사유를 강제하면
  번거롭기만 하다. 적어두면 상태 배지의 tooltip에 함께 뜨고 엑셀에도 나간다.

- **키는 은행 거래고유번호(`TransRefKey`)** 다 — 입출금내역 자체는 바로빌에서 매번 새로 받아오는
  값이라 DB에 없으므로, "이 건은 확인했다"는 표시만 `BankTransactionConfirm`에 따로 저장한다.
  은행이 매긴 번호라 다시 조회해도 같은 값이 와서 확정 표시가 그대로 남는다.
  - 거래고유번호가 없는 응답(구형 `GetPeriodBankAccountLog` 등)은 그 건을 특정할 수 없어 확정
    버튼이 비활성된다.
- **되돌릴 수 있다("해제").** 세금계산서의 승인/확정은 전표를 만들기 때문에 되돌릴 수 없지만,
  이건 검토 표시일 뿐이어서 잘못 눌렀을 때 풀 수 있어야 한다.
- **누가 언제 확정했는지 남긴다**(`confirmedByEmail`/`confirmedAt`). 화면에는 `확정 MM-DD`로 짧게
  보이고, 마우스를 올리면 전체 시각과 확정자가 tooltip으로 뜬다. 엑셀 다운로드에도 `확정`·`확정자`
  열이 함께 나간다.
- 확정 당시 금액도 함께 저장한다 — 나중에 같은 거래의 금액이 달라졌다면 알아챌 수 있게 하려는 것이다.
- **건수와 필터**가 결과 상단에 있다: `전체 38 · 확정 32 · 미확정 6 · 제외 0`. 칩을 누르면 그
  상태만 걸러 본다. 미확정이 남아 있으면 그 칩이 빨간 글씨가 되어 눈에 띈다.
  - **건수는 필터와 무관하게 조회 결과 전체 기준**이다 — 필터를 걸었을 때 숫자까지 줄어들면
    "몇 개 남았는지"를 알 수 없다.
  - **표 아래 합계줄은 없다.** 금액 합계가 필요하면 엑셀로 내려서 보고, 확정/미확정/제외 현황은
    이 필터 칩에 이미 있다 — 같은 숫자를 두 곳에 두면 언젠가 한쪽이 어긋난다.
  - **엑셀 다운로드도 화면에 보이는 것**을 내리고, 파일명에 `_미확정`/`_확정`을 붙인다 — 필터와
    파일 내용이 다르면 헷갈린다.
  - 필터는 **URL에 담긴다**(`?confirm=unconfirmed`) — 다른 탭에 갔다 돌아와도 유지된다(사이드바
    탭별 위치 기억과 같은 규칙).
  - 필터 결과가 0건이면 "미확정 건이 없습니다 — 이 기간은 전부 확정되었습니다"로, 조회 결과가
    아예 없을 때("이 기간에는 입출금내역이 없습니다")와 구분해 안내한다.
  - 상태는 `BankTransactionConfirm.status`("confirmed"/"excluded")에 저장한다. 테이블 이름은 확정만
    담던 시절 이름인데, **이름을 바꾸면 기존 데이터를 잃으므로 컬럼만 추가했다**(기존 71건은
    `confirmed`로 그대로 보존됐다).

### 송금인으로 거래처 찾기 (거래처코드·거래처 열)
은행 거래내역에는 **상대 계좌번호도 사업자번호도 없고 입금자명(`TransRemark`)만** 온다. 그래서
송금인 이름을 거래처 마스터와 맞춰보고, 맞으면 `거래처코드`·`거래처` 열에 보여준다
(`src/lib/bankPartyMatch.ts`).

- **이름 정규화**: 법인 표기와 구분기호를 걷어낸 뒤 비교한다. 은행 쪽 표기가 실제로 이렇게 온다:
  `(주)앱솔브랩` → `앱솔브랩`, `주)신세계인터내셔날`(여는 괄호가 빠져 온다) → `신세계인터내셔날`,
  `범주해운(주)` → `범주해운`, `주식회사이너시아` → `이너시아`. 괄호를 먼저 통째로 지우면
  `범주해운(주)` → `범주해운주`처럼 잔재가 남아서, **괄호 안 법인 표기를 괄호와 함께** 먼저 지운다.
  `대주기업`처럼 이름에 "주"가 들어간 경우는 깎이지 않는다.
- **매칭 강도 3단계**로 구분해서 보여준다 — 자동 추정을 그대로 믿고 쓰면 안 되기 때문이다:
  - `(자동)` — 정규화 후 **완전일치**. 예: `올리브인터내셔널` → `주식회사 올리브인터내셔널`.
  - `(추정)` — **부분일치**. 은행에서 이름이 잘려 오는 경우가 많다: `주식회사리빙크리에이` →
    `주식회사 리빙크리에이터`, `동서콘솔주식회` → `동서콘솔주식회사`.
  - 표시 없음 — 사람이 지정한 것(별칭). 지정은 항상 자동 추정을 이긴다.
- **오답을 막는 규칙 두 개**: ① 정규화 후 **같은 이름이 둘 이상**이면 매칭하지 않는다(틀린 거래처를
  붙이는 것보다 비워두는 게 안전하다). ② 부분일치는 **4자 이상**일 때만 쓴다 — 짧으면 우연히
  포함관계가 생긴다(`한진`이 `한진해운`·`대한진흥` 양쪽에 걸린다). 실제로 `그란데클립코리아`와
  `그란데클립 에프앤비`가 서로 다른 거래처로 정확히 갈린다.
- **지정/변경/해제**: 거래처 열의 `지정`(또는 `변경`) 버튼을 누르면 코드/거래처명 검색칸이 뜬다
  (`PartySearchSelect` — 거래처 마스터에 있는 것만 고를 수 있다). `해제`를 누르면 지정을 지우고
  자동 추정으로 되돌아간다.
- **지정은 거래 1건이 아니라 송금인 이름 단위로 저장된다**(`BankPartyAlias.normalized`가 키).
  같은 거래처에서 입금이 반복되는데 거래마다 다시 고르게 하면 쓸 수 없기 때문이다. 그래서
  `패밀링크`를 한 번 `FAMILINK`로 지정하면 **`(주)패밀링크` 행도 함께** 붙는다(정규화가 같다).
  화면에도 `"{송금인}" 의 모든 거래에 적용됩니다`라고 밝혀둔다.
- 매칭은 **서버에서 계산해 내려준다**(`buildRemarkMatches` → `matches`) — 정규화 규칙을 화면에서
  다시 구현하면 언젠가 어긋난다. 엑셀 다운로드에도 `거래처코드`·`거래처` 열이 함께 나간다.
- 아직 안 하는 것: 이 매칭은 **보여주기만** 한다. 입출금내역을 전표와 자동으로 대조하거나
  전표를 만들지는 않는다.

### 거래확인서 (입금증/출금증)
표 **맨 왼쪽 "확인서" 열**의 `입금증`/`출금증` 버튼을 누르면 그 거래 1건이 A4 한 장짜리
**계좌 거래내역 확인서**로 새 창에 뜬다(`src/lib/bankSlip.ts`). 은행 인터넷뱅킹의
"계좌별거래내역 상세정보"와 **같은 항목·같은 배치**라 결의서에 첨부하면 눈으로 바로 대조된다:

    거래일시  | 2026.07.01 16:56:58
    계좌번호  | 140-016-218130 (신한은행)  | 적요   | 타행PC
    입금액    |          5,737,244 원      | 출금액 |        0 원
    거래점명  |                    기업    | 내용   | (주)앱솔브랩

- **필드 대응**: `적요`=`TransType`, `내용`=`TransRemark`(입금이면 송금인명), `거래점명`=
  `TransOffice`. 은행 양식의 항목 이름이 우리 데이터와 정확히 일치해서 그대로 옮겼다.
- **PDF 라이브러리를 새로 넣지 않았다** — 인쇄용 HTML을 새 창으로 띄우고 브라우저의
  "PDF로 저장"을 쓴다(한글 폰트 문제도 없다). 창이 열리면 인쇄 대화상자가 자동으로 뜨고,
  취소하면 화면에 남아 다시 누를 수 있다. 팝업이 차단되면 화면에 안내가 뜬다.
- **은행 로고나 은행 발행 문서 형식을 그대로 재현하지는 않는다.** 이건 우리 앱이 바로빌
  데이터로 만든 문서이고 은행이 발행한 증빙이 아니어서, 은행 문서와 구분되어야 한다. 그래서
  발행 주체를 Mati-Ni로 밝히고 하단에 출처와 **은행 거래고유번호(`TransRefKey`)** 를 적어
  은행 원본과 대조할 수 있게 했다. **은행 공식 증빙은 인터넷뱅킹에서 받아야 한다**(바로빌
  계좌조회 API에는 증빙 발급 기능이 아예 없다 — 오퍼레이션 61개 전수 확인).
- 상단 "고객명"은 `.env`의 `BAROBILL_CORPNAME`이다(기본값 `주식회사 테크타카로지스틱스`).
- 계좌번호 하이픈은 **확실한 경우에만** 넣는다(신한 12자리 = 3-3-6) — 은행마다 자리수 규칙이
  달라서 잘못 끊으면 다른 계좌처럼 보인다.
- 거래점명의 괄호는 표와 **같은 규칙**으로 벗긴다(`stripParens`를 `bankSlip.ts`에서 export해
  화면과 공유). 송금인 이름에는 적용하지 않는다.

**계좌 추가는 바로빌에서 한다.** 계좌 등록 API(`RegistBankAccount`)는 계좌·인터넷뱅킹 비밀번호를
받아야 해서 일부러 구현하지 않았으므로(위 참고), 새 계좌는 "[관리자] 계좌 등록·관리" 버튼으로
바로빌 화면에서 등록한다. **등록하면 우리 앱은 조회할 때마다 목록을 다시 받으므로 코드 변경 없이
바로 셀렉트에 나타난다.**
